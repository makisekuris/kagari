# 文件归档与版本管理规划

设计讨论截至 2026-11-24。使用者通过微信或 Telegram 要求 Kagari 归档一份附件，之后可用聊天找到对应文档和版本、核对当时的说明、取回原件，或针对原件提问。

## 1. 接入现有渠道和主 Agent

微信和 Telegram 继续通过 `channel.Files` 收发附件。用户明确提出归档时，主 Agent 通过内置工具把已接收的附件 ID 交给归档服务。渠道适配器负责平台的收发和状态，归档服务负责版本、查询和后台处理。当前运行时每次启用一个渠道，实施时分别验证两个渠道使用同一套归档工具。参见 [渠道设计](CHANNEL-DESIGN.md)、[附件接口](../internal/channel/channel.go) 和 [主 Agent 工具注册](../internal/personal/assistant/model.go)。

SQLite 保存归档目录、来源引用和处理状态。私有对象存储（OSS）按版本保存原始字节。主 Agent 通过归档服务调用这些操作。外部应用需要访问同一归档库时，再为这组操作提供 MCP 接入。

## 2. 文档、版本和归档上下文

| 记录 | 保存内容 |
| --- | --- |
| 文档 `documents` | 稳定的 `document_id`、标题、分类、标签。项目归属成为明确需求时，可另加 `project_id`。 |
| 版本 `document_versions` | `version_id`、所属文档、提交时间和顺序、原始文件名、媒体类型、大小、OSS 对象键、来源附件与事件引用、用户备注、简述及其来源和覆盖范围、上传与分析状态。 |
| 提取结果 | 按版本、结果种类和源位置关联，记录状态与存储引用。接入相应处理器后再保存已生成的结果。 |

使用者把修改后的原件明确提交为新版时，沿用 `document_id` 并新增版本。每版保留独立原件、简述和上下文，可以单独取回和比较。修改标题、分类或标签时更新文档记录。纠正简述时更新对应版本的简述。文件相似时，Agent 可以给出候选，使用者明确指明关系后再追加版本。

普通新版在受理时按提交时间线分配顺序，后台上传和分析可以各自完成。「最新版」按提交顺序取最新提交的新版，处理状态用于决定该版此刻能交付什么。用户明确补录旧稿时，记录实际提交时间，并保留用户指定的历史位置。例如已有第二版，今天补录第一版后，「发我最新版」仍选择第二版。

归档记录保留触发这次归档的事件 ID。上传附件和提出归档是两条消息时，也保留文件来源事件。Agent 可以用现有的 `get_event` 或 `get_message` 回读具体历史，分页游标在读取时生成。用户明确希望随文件保留的用途或说明存为备注，参与搜索。参见 [历史读取工具](../internal/personal/agentctx/context_tools.go)。

## 3. 异步归档和简述

1. 主 Agent 调用归档工具，在同一笔 SQLite 事务里登记版本和后台待处理状态。工具返回版本 ID 和当前状态，主 Agent 可以确认「已登记」。同一用户事件以相同参数重试时返回已有版本。
2. 后台从聊天附件读取原件，按该版的对象键上传 OSS。失败重试沿用同一个对象键。后台工作按版本继续，处理快慢不改变已登记的版本顺序。
3. 后台做便于日后发现文件的初步分析，写入一两句话的简述，标明来源以及实际分析的页、段落、工作表区域或时间段。正文无法读取时，可以采用用户提供且能识别文件的说明，并标为「使用者说明」。只有文件名时保留原件，显示「待补充说明」。
4. 原件和简述都就绪后标记「已归档」。原件上传后即可生成下载链接。上传期间，用户要求发回文件且聊天附件可读时，用现有交付能力发回该版原件。用户明确要下载链接时，报告该版的上传状态。

初步分析只取能形成简述的内容。后续读取指定页、OCR、转写、表格区域等工作按请求安排到后台。重复请求可复用同一版本、种类和范围的处理结果。用户只要文件时，取选定版本的原件。

## 4. 工具和渐进披露

| 主 Agent 工具 | 输入和返回约定 |
| --- | --- |
| `archive_attachment` | 指定 `attachment_id`、新文档标题或已有 `document_id`、可选备注。普通追加和显式补录表达为不同的请求意图。登记后返回文档 ID、版本 ID 和处理状态。 |
| `search_archives` | 按标题、标识符、文件名、标签、备注和简述查 SQLite，支持按时间和分类缩小范围。每条候选返回简述、命中依据、匹配版本和最新版状态。已有的提取正文可在后续纳入全文检索。 |
| `get_archive` | 按文档 ID 查看历史，按版本 ID 查看原件信息、备注、来源事件、处理状态和可用的读取方式。 |
| `get_archive_download_link` | 按版本 ID 生成临时下载链接并返回过期时间。对象未就绪时返回该版本的实际状态。 |
| `read_archive_text` | 按版本分页读取初步分析保存的文字，附原件取样范围。复用 `textpage` 控制返回长度，文字还在提取时返回后台状态。 |
| `prepare_archive_attachment` | 指定版本，准备聊天交付用的附件。优先使用可读的聊天原件，之后可以从 OSS 取回。 |
| `update_archive_document` | 修改文档级标题、分类或标签。 |
| `update_archive_summary` | 把使用者明确补充或纠正的说明保存为该版简述，来源标为「使用者说明」。 |

搜索先返回少量候选和简述。比如第一版简述命中「防水质保」，第二版仍待分析，结果展示第一版的依据，并说明第二版内容有待确认。接着要求「发最新版」时选第二版。核对归档缘由再回读历史消息，核对内容再取对应版本的原件或提取结果。

文件中的位置由格式决定。PDF 保留原始页码，有文字层时提取文字，需要时对扫描页做 OCR。Word 按段落和表格定位。Excel 按工作表和单元格区域读取结构化值。图片可提供带区域的 OCR 文字，也可将图片或区域交给支持图像输入的模型。音频可提供带起止时间的转写或指定片段。同一版本可以提供多种结果。记录版本与结果的关系，随实际用例增加单元格、图像或音频读取工具。当前基线已有文本分页和图像分析入口。参见 [文本分页](../internal/textpage/textpage.go) 和 [图像分析](../internal/personal/agentctx/image_tool.go)。

## 5. 实施顺序

1. **归档和取回。** 增加 SQLite 文档与版本记录、OSS 接口和后台上传，先接登记、搜索和下载工具。使用显式用户说明完成简述，跑通一个渠道的收件、归档、查找和原件交付，再验证第二个渠道。
2. **自动简述和版本检索。** 接入首批内容分析，保存简述来源及范围，提供文档详情、历史和指定版本读取。验证补录、并发提交以及旧版命中时的搜索结果。
3. **按需读取更多格式。** 根据实际文件增加 PDF、Word、Excel、图片和音频的处理方式。搜索出现明确的正文关键词需求时再评估全文索引。语义检索、知识图谱和 MCP 按各自的使用需求评估。

首批接入采用 RustFS 的 S3 API 和 path-style 地址。默认区域为 `us-east-1`，启用、桶和凭证的配置见 [配置示例](../config.example.yaml)。轻总结取最多 12,000 个字符的 UTF-8 或 `.docx` 正文。安装 `pdftotext` 后，PDF 取前最多三页的文字层。配置图像模型后支持 PNG、JPEG 和 WebP。扫描件 OCR、表格区域和音频转写适合后续按需增加。

## 6. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| Telegram 或微信收到附件，使用者明确要求归档 | Agent 收到统一附件 ID。请求受理后可查到版本和实际处理状态。 |
| 同一归档请求重试，或原件上传后进程重启 | 查到同一版本，后台沿用该版对象键继续；归档记录可恢复。 |
| 第三版上传中，聊天附件可读，用户要最新版 | 选中第三版并发回原件。用户明确要链接时返回第三版上传状态。上传就绪后可签发链接。 |
| 已有第二版，今天补录第一版 | 两版可分别取回，第一版保留实际提交时间和历史位置，最新版是第二版。 |
| 第二版先提交，第三版先完成后台处理 | 第三版是最新版。随后第二版完成时仍按提交时间线查找。 |
| 文件无法读取正文，但用户给了可识别的说明 | 原件与说明就绪后可完成归档，简述标明依据来自使用者。只有文件名时显示待补充说明。 |
| 第一版命中防水质保，第二版待分析 | 展示第一版匹配依据及第二版状态。随后要求发最新版时，选第二版。 |
| 用户要扫描 PDF 第四页或 Excel 指定区域 | 只请求相应页或区域的提取结果，返回其原件位置。请求原件时以选定版本交付。 |
