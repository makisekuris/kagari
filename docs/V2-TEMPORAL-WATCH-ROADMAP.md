# Kagari 时序与原子性修复及 condition trigger 路线图

状态：2026-11-13，F1–F5 已完成测试与主 Agent review，并按 F1 → F5 → F2 → F3 → F4 分阶段交付；W0 已形成设计草案，W1 待深入讨论，尚不可开始实现。本文归档五项代码审查发现，以及独立于 Schedule 的 condition trigger（条件触发）机制计划。代码审查基线为 `a1793390be459403ff6b24b00362a393d35aec89`。现有事实、拟议契约和验收条件分别记录；功能清单中未勾选的项目尚未完成。

目标是让异步工作的身份、授权、结果和交接状态保持一致：旧回调不能影响新执行；已结案工作有可恢复的交付意图；生成回复与渠道接受分别可查；等待外部条件的任务能够释放执行槽，并在条件满足后可靠推进原目标。

现有领域定义见 [CONTEXT.md](../CONTEXT.md)，模块职责见 [personal 模块说明](../internal/personal/README.md)，Schedule 的已实现行为见 [定时计划设计](SCHEDULE-DESIGN.md)和[实现方案](SCHEDULE-IMPLEMENTATION.md)。condition trigger 的能力名称已确定，持久记录在本文中称“触发记录”；具体类型、表名和字段尚未确定。沿用 W0–W3 编号和本文件路径，便于追踪已有引用；这些内容均为拟议能力。

## 1. 交付顺序

F1、F5 分别交付；F2–F4 先统一交付身份，再按事务保存、投递规则、History 表达顺序集成。每个实现阶段完成测试和主 Agent review，确认结果符合契约后单独提交 commit，再推进下一阶段。W0 是前置设计工作，可在修复阶段开展。W0 完成不自动放行 W1：必须先与使用者深入讨论第 6.1 节的问题，确认设计并记录结论，才能开始 W1 编码。W2 随 W1 设计调整。

| 阶段 | 待办 | 可独立验收的结果 | 准入与依赖 |
| --- | --- | --- | --- |
| 1 | F1 旧回调 | 旧回调不改变新 Run 的状态、成果或预算；正常过期事件不导致服务退出；自身已提交的续跑仍可恢复 | 无，优先实施 |
| 2 | F5 发送回执与关闭错误传播 | 关闭时保存已知发送结果；持久化失败由 `Runtime.Run` 返回 | 无，可与阶段 1 分开交付 |
| 3 | 共享交付契约与 F2 结案提交 | 结案状态、草案及选定附件同事务保存；中断后只生成一份交付 | 固定第 3 节共享契约，并沿用 F1 身份规则；不以 F5 完成为硬依赖 |
| 4 | F3 outbox 有效性与顺序 | 旧输出按规则作废或保留；同 Task 必要保序；独立 Task 不被阻塞 | 阶段 3 的交付身份和消息用途 |

| 6（前置设计） | W0 condition trigger 契约 | 形成身份、授权、状态转换、预算和现有入口影响表；标出 W1 待讨论决策 | 可在阶段 1–5 期间开展；不包含 W1 编码 |
| 7（待讨论） | W1 持久等待与匹配准入 | 经设计确认后，实现可恢复的条件检查、冻结匹配和唯一续跑事件 | 阶段 1、6；第 6.1 节讨论与设计确认完成后方可开始 |

| 后续 | W3 更多外部来源与容量恢复 | 每个来源有独立契约和验收；容量不足与业务失败分开处理 | 阶段 8；按真实业务选择接入项 |

## 3. 五项修复

### F2–F4 共用的交付契约

阶段 3 先固定以下契约，F3、F4 复用同一关系，不各自推导回复归属：

| 对象 | 需要保存或明确的事实 |
| --- | --- |
| 完整交付意图 | 稳定交付 ID、来源事件、适用的 Task/revision/Run、消息用途、文字草案、显式选择且有顺序的不可变附件 ID；无 Task 的回复不伪造 Task 身份 |
| 一次交付的内容 | 一份草案生成多个文字分段和附件发送项；每项关联原交付和顺序，分别记录状态及回执 |
| History | 生成内容关联原交付及其发送项；整体状态由各项事实形成，不维护另一份可独立修改的投递状态 |
| 幂等与补发 | 同一交付的恢复或发送重试复用原身份；用户显式补发建立新交付并引用原成果，不覆盖旧回执或未知结果 |
| 有效性 | 来源身份固定保存；是否仍允许发送按 F3 规则判断，不能通过当前 Event/Task 状态反推历史来源 |

提交顺序为：结案状态与交付意图同事务保存 → 事务外整理文字和分段 → 同事务保存 History、完整 outbox 及交付转换结果 → 渠道发送 → 保存各项回执。来源事件的完成与后续工作放行沿用现有事务约束。交付意图已保存但 outbox 尚未生成时，恢复扫描必须能找到它；outbox 已提交时不得再次整理并追加另一份发送项。

完整交付意图不代表渠道已经接受；Task 已完成、生成内容已保存、部分渠道接受和全部渠道接受分别可查。附件不可用等交付失败保留具体原因，不回滚已完成的业务检查。阶段 3 的 schema 设计同时覆盖 F3 的消息用途和 F4 的一对多关联，避免后两阶段各建一套身份。

阶段 3 的实施约定：

- 使用独立的交付记录保存草案与来源；History 和 outbox 引用其 ID。每个交付显式保存所属 Task 的 revision/Run；涉及多个 Task 时保存各自归属，不把 Event 上的单个 Task 字段当作完整关系。
- `SettleTask` 显式接收交付草案和有序附件 ID，摘要继续表示任务成果。同一来源事件、Task 和 revision 只有一个结案身份；相同载荷重试返回原结果，不同载荷拒绝覆盖。
- 已提交结案意图的事件恢复时，直接读取原意图、整理文字并完成事件，不再次调用结案工具或重选附件。事件完成、History、所有发送项及意图转换在同一事务提交；事件未完成时沿现有 `Recover` / `ClaimEvent` 路径恢复。
- 普通回复、等待提示、计划通知也建立交付记录，各自保留用途；一个事件可以包含多份交付。发送项仍各自保存回执，交付记录不复制一份可独立修改的“已经送达”状态。
- 回复整理只接收草案，不接收重新选择附件的权限。附件在提交结案时校验，生成发送项时复核；不可用时保留原选择和失败原因，并给出附件不可用的反馈，不能将失败交付标成完整成功。
- 本阶段升级到 schema 5。schema 4 及更早数据库拒绝启动并保持原样；需显式配置新路径，不提供隐式迁移。

### F1 旧回调在同一 revision 下进入主对话并导致 Runtime 退出

优先级：P1。已复现旧回调绕过入口检查后，`turn` 返回 `personal: stale or unauthorized task callback`。按当前 Runtime 的错误传播规则，该返回会停止其他 worker 并退出服务。

业务顺序：Run A 正在比较数据库产品；用户“继续补查价格”的消息先入队；A 随后失败并产生回调；主对话先处理用户消息，创建同一 revision 的 Run B；B 在旧回调处理前或处理中完成；旧回调 A 看到 Task 为 awaiting_review，进入结案处理并被 Store 拒绝。

根因：入口检查目标 revision 与取消状态，Store 写操作还检查最新 Run。Task revision 表示目标版本，不能替代具体执行身份。`CompleteEvent` 虽能丢弃旧回调输出，但这条路径在到达它之前就返回错误。

涉及 [runtime_conversation.go](../internal/personal/service/runtime_conversation.go)、[tasks.go](../internal/personal/sqlite/tasks.go) 的 `requireCallback`、[event_completion.go](../internal/personal/sqlite/event_completion.go) 的 `currentTaskCallback`、[task_execution.go](../internal/personal/sqlite/task_execution.go) 的 `AccountEvent`，以及 [runtime.go](../internal/personal/service/runtime.go) 的错误传播。

- [x] 将“已被后续执行取代”表示为明确的业务结果，入口遇到它时完成旧事件并记录原因，不调用模型、不修改当前 Task。
- [x] 统一入口、变更提交、事件完成、恢复和预算记账对身份的解释；列出各操作允许的结果，提交时保留最终校验。
- [x] 区分“允许再次变更 Task”和“允许结束本回调、释放它已创建的续跑”。回调自己创建的下一 Run 仍是有效交接，不能因最新 Run 已变化而误删。
- [x] 数据库错误和不变量破坏继续返回错误；不通过吞掉所有错误解决过期回调。

验收：固定 A → 用户续跑 B → B 完成 → A 回调的顺序；A 被静默完成且不调用模型，B 的状态、成果和预算不变，后续用户事件仍可处理。同时覆盖 B 尚在运行、目标 revision 已更新、Task 已取消，以及回调已经提交自身续跑后重启的情况。注入数据库错误时仍向外报错；验证旧回调不调用模型、不增加预算，自身续跑只放行已提交的同一个 Run，不能只断言旧事件已完成。

### F2 Task 结案与完整交付意图之间存在恢复缺口

优先级：P2。已复现 Task 保持 completed、附件仍存在，但恢复后的 outbox 只有文字。

业务顺序：用户要求生成并发送云厂商比较报告；阶段保存报告附件；主 Agent 调用 `settle_task`；最终输出选定附件；整理回复时服务中断；`CompleteEvent` 尚未保存 outbox。恢复只使用 Task 摘要，丢失本轮附件选择。

涉及 [task_lifecycle.go](../internal/personal/sqlite/task_lifecycle.go) 的 `SettleTask`、[runtime_conversation.go](../internal/personal/service/runtime_conversation.go) 的 `publish`/`recoverTurn`、[event_completion.go](../internal/personal/sqlite/event_completion.go)、[replies.go](../internal/personal/sqlite/replies.go) 及 assistant 的结案/最终输出契约。

- [x] 按共享契约保存完整交付意图；在结案提交前完成草案和附件选择。
- [x] 调整 `settle_task` 参数和 `SettleTask` 接口，将状态、Task 摘要、交付草案、显式附件 ID 及必要的检查评估一并提交；Task 状态与交付意图同事务保存。摘要与草案职责分开，允许有摘要而交付只选附件。适用于 completed、failed、waiting_input 等需要反馈的结案路径，Runtime 自行结案和恢复路径也遵循同一规则。
- [x] 结案后的最终输出与回复整理消费已保存意图，不再次决定交付附件；模型整理文字、分段和渠道发送都在事务外执行。
- [x] 同一结案身份和相同载荷重复提交时返回已保存结果；身份复用但草案、附件或结案决定不同则明确拒绝。与 Schedule 检查进度的记账保持原子和幂等。
- [x] 已保存意图恢复时使用同一身份继续生成 outbox，不重放结案工具，不重新选择文件。
- [x] 保留“保存附件”和“选择发送附件”的区别。阶段产生的所有文件不自动成为交付物。
- [x] 附件删除或不可用时保留明确失败原因，生成符合当前附件规则的反馈；不能静默把交付标为完整。

验收：在结案前、结案与意图提交后、回复整理中、outbox 提交后分别中断；恢复后交付身份、草案归属和附件 ID/顺序一致，不重复结案、不重复入队。事务失败时状态和意图都不提交；重复请求不重复推进检查进度，身份冲突不覆盖旧意图。覆盖 completed、failed、waiting_input、仅附件交付、多版本同名文件、多个附件及恢复前附件删除。仅附件交付仍保存任务摘要，是否发送文字由交付意图明确。定时检查成功进度仍与实际发送分开，不因投递失败回滚已经完成的检查。

### F3 待发结果缺少版本有效性和跨事件顺序规则

优先级：P2。已复现新事件回复越过退避中的旧回复，以及 Task 取消后旧待发结果仍可被领取。是否作废历史成果需要明确业务规则，不能从“取消计算”自动推导出“撤回所有消息”。

业务场景：旧报告推荐 A，发送限流；用户改变约束后，新报告推荐 B；B 先发出，A 后重试成功。另一种情况是用户明确说“不用发结果了”，取消 Task 后，原 pending 报告仍然发出。

审查基线中的 [delivery.go](../internal/personal/sqlite/delivery.go) 只阻止同一 event 的后续分段越过 pending/sending 的前序分段；[task_lifecycle.go](../internal/personal/sqlite/task_lifecycle.go) 的取消不撤销普通 outbox。入队前回调校验不能覆盖入队后的状态变化。

阶段 4 固定以下实施契约：

- 停止投递与取消计算是两个操作。Task 级停止跨 revision 生效，直到直接用户显式恢复；交付级停止只作用于指定交付。`resume_task_delivery` 只允许未来交付，旧 suppressed 项保持原状；需要旧成果时调用 `resend_delivery` 创建新身份。
- 控制请求按来源 event 与请求键幂等，同身份不同载荷拒绝。停止/恢复和确认意图同事务保存，确认写明实际操作及时间。取消计算同样保存控制确认，但不自动执行停止投递。同轮还有独立查询或任务操作时，其回复另存一份交付并保留自己的归属，不能用控制确认覆盖它；未解决失败及必要问题同样单独保留。
- `suppressed` 是保留原因的终态，不删除 History 或 outbox。Task 级停止影响成果和临时状态，并抑制当时已存在的历史补发；后来的显式历史补发是一次新的直接授权。自动版本检查不会抑制历史补发或控制确认。
- 同一 Task 的持久交付 ID 决定顺序；交付内部按发送项序号。尚未整理出 outbox 的旧意图也阻塞其后成果。控制确认可以越过成果退避，多个 Task 的合并回复保存所有所属 Task，无关 Task 的交付不互相等待。合并回复任一归属失效时抑制整份剩余内容，不能在发送时重新拆分或改写原草案。
- 意图生成、目标更新、控制操作和领取都复核规则；整理期间被停止的交付保存抑制事实并结束来源事件，不重新进入决策模型。已经 sending 的项继续保存已知结果；若回到 pending，则再次复核停止规则。
- failed 或 uncertain 项使同份交付的剩余 pending 项抑制，保存前缀的已知回执，释放后续交付；重启将 sending 改为 uncertain 时执行同样规则。

消息用途、撤销范围和领取条件如下；完成记录需列出实际验证：

| 变化或消息用途 | 已实现的处理规则 |
| --- | --- |
| Task 目标 revision 变化 | 尚未发送的旧版本自动成果作废；需要历史成果时由用户显式补发，并标明原版本 |
| 同 revision 创建新 Run | 不仅凭 Run 变化抹去已形成的阶段成果；成果按同 Task 顺序发送并保留阶段归属，失效的临时状态通知抑制 |
| 仅取消计算 | 停止执行和自动续跑，保留已有成果及其交付记录；不隐含撤销全部待发成果 |
| 明确“不要再发” | 保存指定 Task 或交付的停止投递范围，撤销范围内未开始发送的内容；范围包括尚未生成 outbox 的意图，后续入队和领取也复核该规则。显式补发或恢复发送需要直接用户授权 |
| 控制操作确认 | 记录操作实际结果，不因目标 Task 已取消而被误作废；若控制已被后续操作取代，说明原操作及其时间归属 |
| 显式补发历史结果 | 创建有直接用户授权的新交付，引用原版本成果；不将其冒充当前版本，不修改旧投递记录 |
| 已开始发送或已发送 | 不承诺撤回；保存已知结果，未知结果仍为 uncertain，已经接受的内容及回执保留 |

- [x] 为 outbox 保留不可变的来源执行身份和上述消息用途；停止投递与取消计算使用明确的操作语义，不能只根据 Task cancelled 状态推断。
- [x] 作废或抑制保留状态与原因，History 能区分未交付和已接受；将现有等待提示抑制路径纳入规则，不能另留一套相互矛盾的状态解释。
- [x] 在领取事务内复核当前有效性，并在修改目标、停止投递等事务中维护撤销状态；明确已经开始的外部发送不保证撤回。
- [x] 同一 Task 的成果交付按持久顺序发送，各交付内部按分段和附件顺序发送；独立 Task 不共用阻塞队列。跨 Task 的合并回复必须显式记录归属，不从一组回复反推唯一 Task。
- [x] pending 退避和 sending 阻止需要保序的后续成果；旧消息作废后释放后续交付。failed 或 uncertain 出现在交付中途时，停止自动发送同一交付的剩余项并记录原因，释放后续独立交付；不得把前一份内容标为完整送达，也不得自动重发 uncertain 项。

验收：逐行验证上表，包括同 revision 新 Run 与目标 revision 变化的不同处理；同一 Task 的旧结果退避、新结果入队；改目标与领取同时发生；取消计算、停止投递分别发生在 pending、sending、sent 三个时点；交付意图已保存但尚无 outbox；文字已发而附件未发；首段 failed 或 uncertain 后同份剩余项停止、后续交付释放；控制确认和显式补发不被误抑制；无关 Task 不被阻塞。断言具体可发送内容、顺序、作废原因及已知回执，不只断言 SQL 执行成功。

### F4 History 没有区分系统已生成与渠道已接受

优先级：P2。已复现 pending 回复作为普通 assistant 历史进入下一轮上下文；是否造成误解取决于具体模型与对话。

业务场景：系统生成“是否扩展到海外产品”，但发送失败；用户针对更早的信息回复“可以”。模型可能把未送达的问题当作共同上下文。用户追问“报告呢”时，也需要区分报告没生成和报告没发成功。

涉及 [replies.go](../internal/personal/sqlite/replies.go) 的历史写入、[event_queries.go](../internal/personal/sqlite/event_queries.go) 的 `History`、[events.go](../internal/personal/events.go) 的 Message，以及 assistant 上下文组装、摘要和回复关联。

- [x] History 保留已生成内容，通过共享交付身份关联多个文字分段和附件项，逐项返回 outbox 身份、状态、原因与已知回执；不能用单个 `OutboxID` 或单一 sent 标记代表整份回复。
- [x] 普通回复、等待提示和 Schedule 通知采用同一关联规则；无 Task 的回复仍能准确查询投递状态。condition trigger 在 W2 接入时必须复用该规则，其通知不属于本阶段已实现范围。
- [x] 把“渠道已接受”与“用户已阅读”分开，普通发送回执不证明已读。
- [x] 待发、failed、uncertain、作废或抑制的内容不能被模型当作已告知用户；部分成功只表明具体成功项已被渠道接受。生成过的成果仍可被复用，避免重复研究。
- [x] 历史压缩保留影响理解和授权的投递状态；裁剪正文不丢失这类事实。
- [x] 继续优先使用精确的 reply-to 关联。没有关联的“可以”“继续”不自动确认一条尚未送达的问题。

验收：pending/failed/uncertain/作废/部分成功分别进入下一轮上下文；一份回复含多个分段和附件时，逐项回执与整体完成程度一致；已知远端消息的回复精确关联到对应项，而非同事件任意 History。覆盖普通回复、等待提示、Schedule 通知和上下文裁剪；仅凭未送达提问和含糊同意不能扩大任务范围。主要测试检查状态与关联数据，模型测试再检查具体业务判断。

阶段 5 的实施契约：

- `DeliveryProgress` 是读取时从 outbox 生成的快照，不新增可独立写入的交付状态。逐项保留分段序号、附件 ID、状态、原因、尝试次数、下次尝试时间及准确回执；至少存在一项、全部为 sent 且无附件准备错误时，`fully_accepted` 才为 true。错误通知发送成功不代表原附件交付完成。
- History、精确回复、`get_message`、交付查询和诊断复用同一投递快照。回复通过具体 outbox 项关联对应交付和 History，单个 Task 归属从固定 scopes 得出，多 Task 回复保留歧义；不再借用同事件的任意 History 或 Task。
- 上下文与工具压缩可省略正文，必须保留交付身份、全部发送项及状态、回执和控制结果，并标记正文省略；完整正文可回查。必要事实本身超过输入上限时明确返回容量错误，不能悄悄丢弃未送达事实。默认 trace 省略草案和发送项正文，完整模式才展示正文。
- 提示词区分生成、渠道接受和已读，复用已有成果，并要求无精确关联的含糊同意先澄清。验收使用结构化状态、真实上下文压缩链路和脚本化模型响应；不将提示词或模拟模型测试当作任意模型都不会误判的保证。

### F5 服务停止时丢弃已经取得的成功回执

优先级：P2。已复现 Send 返回成功 message ID，同时父 context 被取消后，outbox 仍停在 sending，重启转为 uncertain。

业务场景：报告已经被渠道接受，服务恰好关闭；本地丢失成功回执，无法准确关联用户对报告的回复。

涉及 [runtime_delivery.go](../internal/personal/service/runtime_delivery.go) 的 Send 后处理、[runtime.go](../internal/personal/service/runtime.go) 的 worker 错误汇总，以及 [event_completion.go](../internal/personal/sqlite/event_completion.go) 的 sending 恢复。任务记账已有短时、脱离父级取消的收尾方式，可按同样原则复用。当前外层 worker 仅在父 context 未取消时汇报错误，因此只修复 `deliver` 的 context 仍可能使收尾持久化失败被当作正常退出。

- [x] Send 已返回确定结果时，以有界的收尾 context 保存回执或确定失败分类，服务退出等待这次持久化结束。
- [x] 持久化本身失败仍明确返回错误；远端结果未知时保留 uncertain，不自动重发。
- [x] `Runtime.Run` 等待收尾完成并保留持久化失败，包括收尾 context 超时；正常的父 context 取消不代表收尾失败可以忽略，不能仅凭父 context 已取消就丢弃 worker 的错误。
- [x] 复用现有 UpdateDelivery 的回执幂等规则，避免同一成功回执被重复处理成新发送。

验收：Send 成功与取消同时发生后保存 sent 和准确回执；确定失败仍保存原分类；真正未知结果仍 uncertain。覆盖回执入库失败、收尾超时和重复保存；除 `deliver` 单测外，通过 `Runtime.Run` 验证服务等待保存结束、保存成功后正常退出、保存失败时返回错误。同一进程在远端成功后立即崩溃的窗口仍可能不确定，不据此宣称 exactly-once。

## 4. condition trigger 的业务范围

condition trigger 在本路线图中的目标是：绑定一个尚未完成的 Task，在外部条件尚未满足时释放执行槽，保留已完成成果；条件满足且当前授权有效后，通过现有入口创建该 Task 的下一 Run。名称不预设条件解释器、轮询方式或证据存储结构，这些需要在 W1 开始前讨论。

使用者已提出可采用类似 Lody 的代码执行层来表达 condition loop。候选方案、业务完成标准和 W2 拆分见 [condition trigger 设计讨论](V2-CONDITION-TRIGGER-DESIGN.md)。代码层作为条件检查手段纳入评估；是否匹配、如何接回原 Task 及如何完成交付仍由业务契约约束。运行时和首个真实来源尚未确认。

| 业务问题 | Schedule | condition trigger |
| --- | --- | --- |
| 典型请求 | 每天检查一次厂商更新并报告 | 等正式价格发布，再完成这份比较 |
| 工作身份 | 每次触发创建独立 Task | 沿用原 Task，续跑产生新 Run |
| 成果与工作区 | 各 Task 独立 | 继续使用原任务已有成果 |
| 执行预算 | 每个周期有独立 Task 预算 | 沿用原 Task 剩余预算，不因唤醒重置 |
| 触发结束 | 计划持续到暂停或取消 | 一次等待最多接入一次续跑；再次等待显式新建记录 |
| 时间含义 | cron 到期、检查区间和覆盖进度 | 下次检查时间、等待截止时间和证据采集时间 |

候选业务例子：采购比较已完成性能和部署条件研究，缺少厂商正式价格。主 Agent 为原 Task 登记条件触发；宿主按限定来源检查价格发布状态；命中后保存证据；主 Agent 在同一目标下补齐价格并交付。等待期间不占 Task 执行槽，也不让模型在一个长工具调用中 sleep。“价格发布”仅用于讨论，尚未选定真实来源或承诺将其作为首个适配器。

首版候选范围是有类型、可验证的条件及一个实际需要的只读数据源。条件未满足、观察失败、证据不完整需要分开；网页抓取成功本身不能证明“正式价格已经发布”。是否需要模型判定、如何保存模型判断与宿主来源事实，以及检查时长与用量上限，均列入 W1 讨论。不得先实现通用检查框架，再补首个业务需求。

Schedule 仍负责周期性新任务，不通过临时 Schedule 模拟原任务续跑。W0/W1 可评估复用现有定时唤醒代码，但 condition trigger 的状态、授权和完成条件独立定义。

## 5. W0 condition trigger 身份与状态契约

W0 交付设计结论和影响清单，不实现检查 worker、来源适配器或新 schema。下列约束与候选转换用于 W1 讨论；涉及暂停、预算恢复、首次数据源和证据语义的选择，需要在第 6.1 节形成确认后的方案。

### 5.1 身份和授权

- [ ] 触发记录保存稳定 ID、创建与授权来源事件、Task ID/revision、登记时的锚点 Run、条件定义版本和固定续跑请求身份；这些身份与一次检查尝试的身份分开。
- [ ] 原目标内的等待可由有效任务回调登记；新增目标、扩大访问范围和增加预算仍需直接用户授权。执行器可报告等待建议，不能绕过主 Agent 和 Store 自行扩权。
- [ ] 首版建议同一 Task 最多一个未结束的自动等待，先解决单一等待到续跑；复合条件与多个并行等待以后按真实业务增加。
- [ ] 同 revision 的手动续跑也会改变执行身份。首版建议直接取代旧触发记录，不自动重新绑定；是否采用该规则在 W1 讨论中确认。优先用已有 Run ID 和父子关联表达，确有缺口再引入额外 generation。
- [ ] 条件触发事件携带可验证的来源，只能操作原 Task，不能伪装成用户事件，也不能冒用过期 EventTask 回调权限。
- [ ] 检查现有 schema 限制：`personal_events.run_id` 有唯一索引，不能把锚点 Run ID 直接作为另一条回调事件的 `run_id`；`personal_requests` 对结果形态有 CHECK 约束，复用触发登记、控制和接手幂等记录前必须明确如何表达。不能为满足约束伪造 Run。

### 5.2 生命周期与预算

建议把观察、匹配、准入、接手分别记录。候选阶段为 observing → matched → enqueued → consumed；终结原因包括 cancelled、expired、superseded、failed。暂停和阻塞原因与阶段分别表达，避免把暂时阻塞改写成条件从未匹配。`consumed` 表示已有可追踪的接手结果，具体结果可以是关联 Run、等待用户或终止；不表示 Run 已执行或 Task 已完成。阶段名与持久字段均待设计确认。

需要固定以下联动关系；表中涉及实现方式的建议不能替代 W1 设计确认：

| 触发记录的变化 | Task、Run 和事件的约束 |
| --- | --- |
| 登记条件触发 | 原 Run 已保存阶段成果并结束；触发登记与 Task 进入外部等待同事务提交；来源事件完成后才允许检查或接手 |
| 条件首次匹配 | 冻结匹配事实和来源证据，Task 在成功准入前仍处于等待；不直接启动执行器 |
| 条件未满足 | 更新下次检查和检查结果，不创建 Run、不主动发消息 |
| 观察失败或证据不足 | 与未满足分开记录；按已确认的重试、上限和终结规则处理，不伪造一次成功判断 |
| matched 时预算不足 | 保留匹配及阻塞原因，Task 显示 waiting_budget；追加预算后的处理方式需与现有 `ContinueTask` 一起确定 |
| 触发记录到期、失败或被单独取消，且无新 Run | 不能让 Task 永久留在无人推进的外部等待；建议转 waiting_input 并说明原因。预算仍不足时保留 waiting_budget；Task 已被取消或完成时保留其现有终态，同时记录触发结束原因 |
| 暂停发生在检查中 | 阻止后续检查和准入；已领取检查的迟到结果不能改变暂停后的状态。如何废弃尝试身份在 W1 固定 |
| 暂停发生在 matched 或事件已入队时 | 保留匹配和固定接手身份；阻止自动接手，恢复时重新检查资格。暂停事件不得阻塞主对话处理其他事件 |
| 暂停发生在 Run 已创建但尚未开始时 | 需定义同一 Run 的挂起与恢复方案，避免将 cancelled Run 重新标为 running，也不能恢复时另建第二个 Run；执行前复核必须覆盖这一窗口 |
| Task 取消、修改目标或手动续跑 | 在相应事务中结束或取代旧触发记录，阻止它的未执行续跑；保留旧证据和已完成成果 |
| Run 已开始 | 后续控制通过现有 Task/Run 取消语义处理；不能将“触发记录已取消”描述为执行器已经停止 |
| 接手未创建 Run | 记录等待用户、终止或阻塞等具体结果，并同步 Task 状态；不得留下 consumed 但结果不可查的记录 |

- [ ] Task 用明确的“等待外部条件”状态表达停驻；不混用 waiting_input、waiting_budget 或 running。具体枚举在 W0 确定。
- [ ] 原 Run 已保存阶段结果并结束；恢复创建下一 Run，不把旧 Run 重新标为 running 来模拟模型调用位置恢复。
- [ ] 登记、匹配、入队、创建 Run、结束来源事件各自的事务边界与恢复入口明确；不在数据库事务中执行外部检查或模型调用。
- [ ] 空等时间不计入 Task 执行预算；条件检查单独记录耗时和调用数量，需要模型时还记录模型用量。明确单次检查和累计检查上限，不能仅限制单次超时。
- [ ] 触发后的主 Agent 续跑决策及实际 Run 沿用原 Task 剩余预算；新事件的记账不能因只识别 `EventTask` 而漏计，登记回调的最终记账也不能被等待状态绕过。
- [ ] Task waiting_budget、cancelled、completed 或目标已变更时不能自动准入。预算不足保留可查询原因，只有用户明确追加后才能重新评估。
- [ ] 区分单独取消条件触发、取消 Task 和停止投递；前两者的状态转换按上表确定，发送行为沿用 F3。
- [ ] 明确检查超时、间隔、匹配截止、准入有效期、连续失败总尝试次数及计数重置条件，写明单位、时间来源与配置来源。总尝试次数包含首次检查，恢复或重启不得隐式重置累计限制。
- [ ] 首版就定义自动续跑和重复登记同类条件的最小累计限制，说明按 Task、目标版本还是派生关系统计，以及谁能重置；不推迟到 W3 后才限制“醒来又登记”的重复过程。具体数值与统计范围在 W1 讨论确认。

### 5.3 与现有入口的关系

候选流程：登记条件触发 → 宿主检查 → 保存匹配 → 复核资格并入队来源事件 → 主 Agent 处理 → 正常 ContinueTask → 正常 ClaimRun/Execute。

主 Agent 可依据证据继续研究、报告限制或要求用户输入，但事件授权只覆盖原 Task。对该事件的续跑必须使用固定请求身份，并在同一事务记录它关联的新 Run。准入、模型处理和 Run 实际开始分别复核适用的当前状态，入口检查不能代替提交校验。

补充材料、修改目标、人工续跑、追加预算和恢复条件触发分别列出效果。当前 `ContinueTask(extendBudget=true)` 会同时创建 Run，不能直接当作“只加预算，再等待条件触发”的接口。需要决定沿用人工续跑并取代旧触发记录，还是提供独立预算调整后重新准入的行为，不能在实现时混用两者。

Schedule 产生的 Task 继续沿用原 occurrence 和冻结检查区间；外部等待是否让后续周期 skipped_busy、暂停 Schedule 是否影响已有触发记录，需明确写入状态表。“不占执行槽”本身不决定 Schedule 的忙碌规则。

W0 验收：交付上述身份和状态表、每种操作的授权来源、提交边界、Task/Run/事件结果、预算归属及受影响入口清单；所有待定项转入 W1 讨论清单。使用“匹配后暂停”“已建 Run 未开始”“触发到期无续跑”“用户补材料或预算”“Schedule 后续周期”逐项走查。完成 W0 只表示设计准备完成，不表示 W1 已获准实施。

### 6.2 设计确认后的候选实现范围

以下是讨论基础，确认后按最终设计调整。最小持久信息包括条件与版本、目标和授权身份、下次检查时间、匹配截止与准入有效期、当前检查身份、检查结果与错误、累计用量、冻结的匹配证据、固定续跑身份、暂停及阻塞原因、已关联事件和 Run。表结构按已确认的不变量设计，避免在多个表维护同一事实的可写副本。

- [ ] 检查领取与结果提交都校验当前触发记录及检查尝试身份。检查期间暂停、取消或替换后，旧检查结果不能复活等待或覆盖新定义。
- [ ] 条件首次匹配时，将结果、宿主捕获的证据、来源版本及固定续跑身份在同一事务保存。成功提交后不再运行原条件程序。
- [ ] 匹配后重新检查目标、授权、停止状态、预算和证据适用性。重检“是否允许动作”不等于重跑“当时是否匹配”。
- [ ] 不可变历史事实可继续作为证据；依赖当前状态的证据若被新版本取代，阻塞或结束该等待，不能默默替换已冻结的匹配。若需新条件判断，创建有明确关系的新等待。
- [ ] 通过一个事务保存入队事件与触发记录的关联和阶段，唯一约束保证重复检查、重启恢复或重复外部通知只接入一次。
- [ ] 主对话繁忙时持久排队，不丢弃唤醒，也不启动第二套模型执行入口。
- [ ] 按已确认的时间规则处理匹配截止和准入有效期，匹配后等待很久不能默认永久有效。
- [ ] 已入队但尚未执行的续跑，仍受后续取消、暂停、目标变更和手动续跑约束。
- [ ] 实现首个已确认的只读来源及分类结果，不以模拟来源通过代替真实来源接入；常规回归使用保存的来源样本和可控时钟，不依赖在线页面恰好发生变化。
- [ ] 将检查上限、重复登记限制、到期和永久失败后的 Task 转换一并实现；预期来源故障按其分类处理，数据库错误和不变量破坏继续报错。

### 6.3 设计确认后的阶段验收

| 场景 | 必须观察到的结果 |
| --- | --- |
| 等待中或检查中重启 | 触发定义和累计计数保留；按确认规则恢复检查，旧尝试不能覆盖新尝试 |
| 匹配提交后、入队前重启 | 保留同一匹配和续跑身份，恢复产生同一关联事件；不重跑已经成功提交的条件判断 |
| 重复检查、重复通知或重复恢复 | 同一触发记录最多产生一个有效接手事件；唯一约束保证身份映射不分叉 |
| 证据离开来源最近记录窗口 | 已冻结证据仍可查，不能因原条件后来读不到该事件而退回 observing |
| 证据未知、失效或匹配已过期 | 按确认规则阻塞或终结，并展示原因；不默默替换冻结证据 |
| 暂停、取消与匹配或入队交错 | 以事务顺序决定结果，迟到检查不能复活记录；恢复不重复入队；其他事件继续处理 |
| 同 revision 手动续跑或目标变化 | 原触发记录按确认规则被取代，不再启动旧续跑 |
| 条件匹配但预算不足 | 匹配保留、无自动 Run、阻塞原因可查；只有已确认的用户操作能解除 |
| 次数或成本达上限、到期、永久失败 | 不再无限检查或重新登记规避上限；无续跑时 Task 有明确后续状态 |
| 首个真实数据源 | 未满足、匹配、观察失败和证据不足有可重复样本；来源身份与证据吻合 |

这一阶段验收到持久检查、匹配和唯一事件交接；主 Agent 实际创建 Run、执行并交付成果由 W2 验收。

## 7. W2 接入主 Agent、执行与恢复

W2 在 W1 设计确认且相关持久契约验收后实施，完整用户行为还依赖 F2–F4。新增状态与来源必须沿现有主对话及 Run 入口处理，不能另开模型执行通道。

| 子阶段 | 范围 | 独立验收 |
| --- | --- | --- |
| W2.1 | 工具、查询和上下文表达 | 授权来源正确，等待条件、匹配证据和阻塞原因可查 |
| W2.2 | 条件事件接手、固定请求与 Run 关联 | 中断或重复接手仍关联同一个 Run；未创建 Run 时也有明确结果 |
| W2.3 | 执行前复核、预算与输入交接、恢复 | 暂停取消阻止未开始的续跑；原成果和工作区保留；预算不重置 |
| W2.4 | 首个真实业务及正常交付 | 原 Task 完成业务目标，附件和回执准确，Schedule 检查区间不被改写 |

各子阶段分别测试、review 和提交；具体接口随 W1 设计确认后固定。

- [ ] 提供登记、查询、暂停、恢复和取消等待的工具及只读诊断；结果说明正在等什么、下一次检查时间、已命中的证据和阻塞原因。
- [ ] 任务查询和主对话上下文展示等待状态，区分“还没满足条件”“已经匹配但未准入”“已排队”“正在执行”。
- [ ] 新事件的来源校验由 Store 执行；工具授权、`ContinueTask`、事件预算记账及 Runtime 的等待、恢复、完成处理都理解该来源，不将其当作直接用户授权。
- [ ] 续跑沿用原 Task 的目标、成果、工作区、有效记忆规则、材料授权、待处理输入和剩余预算。触发记录中冻结的续跑说明不能覆盖后来已授权的更改。
- [ ] 检查所有依赖 Task 状态和事件种类的消费者：输入关联与交接、回复组关闭、等待提示抑制、任务查询、上下文裁剪及诊断；按已确认规则理解外部等待，不能只新增枚举和工具。
- [ ] 入队、创建 Run、结束来源事件分别可恢复。已有 Run 时放行同一个 Run；尚未创建时按持久意图和固定身份恢复接手，不重新运行开放式模型工具来猜测是否已经续跑。
- [ ] `consumed` 表示已有可追踪的接手结果，不表示 Run 已执行或 Task 已完成。交接若没有创建 Run，也必须记录结束、阻塞或等待用户的具体结果。
- [ ] ClaimRun 后等待任务锁、取得锁后实际开始执行的窗口都受来源状态约束；结合现有 `BeginScheduledRun` 所在入口统一复核。取消已创建但未开始的续跑时，同一事务更新相关工作状态；暂停按 W1 确认的方案保留接手身份。
- [ ] 若等待属于 Schedule 产生的某次 Task，沿用该 occurrence；不创建新周期、不改写冻结区间，不让观察到区间外的新事实自动计入旧检查进度。明确该 Task 等待时后续周期的 busy/skip 规则。
- [ ] 普通轮询和条件未满足不主动发消息；登记结果、需要用户处理的阻塞及最终成果遵循现有反馈规则，通知走 F2/F3/F4 的交付流程。

验收采用 W1 已确认的真实业务场景；若选择价格来源，则为“已完成性能研究，等待价格，继续比较并发送报告”。断言 Task ID 不变、Run 身份变化、旧成果及工作区保留、预算不重置且主 Agent 决策耗时记账正确、附件准确、条件不重复触发。

另需覆盖：来源事件处理中重启；已创建 Run 但来源事件未结束；ClaimRun 后等锁期间暂停或取消；接手未创建 Run；用户补材料、修改目标、追加预算和手动续跑；等待到期后 Task 可继续处理；一个等待不阻塞其他 Task 和主对话。Schedule 用例断言后续周期遵守确认后的 busy/skip 规则、原 occurrence 和冻结区间不变、区间外证据不自动推进旧检查进度。通知与最终交付经过 F2–F4，部分投递成功可查询。

## 8. W3 按业务扩展

- [ ] 外部事件适配器：根据实际需要增加发布状态、CI、审批或长任务完成等来源；每种来源定义稳定身份、版本、新鲜度、证据完整性和去重规则。
- [ ] 容量恢复：将结构化的 provider 容量不足与模型业务失败、Task 预算不足区分；保存未完成意图和可确定的已完成结果。
- [ ] 额度重置时间只安排复查，未知或过期的容量观察不能判定可用；未确认副作用不得被自动重放。
- [ ] 按新业务调整检查与自动续跑策略，沿用 W0/W1 已确认的累计限制；不以新增数据源或重启重置计数。

验收按接入项分别定义：每种新来源覆盖稳定身份、版本、新鲜度、证据缺失、重复通知和重启；容量恢复覆盖结构化容量不足、未知及过期观察、复查后仍不足、恢复可用和存在不确定副作用。不得把复查到期视为容量已恢复，也不得重复执行未确认结果的副作用。

首版的代码执行层按真实业务讨论并确定能力范围，候选方案见 [condition trigger 设计讨论](V2-CONDITION-TRIGGER-DESIGN.md)。通用工作流图、多任务协作等待、任意工具调用位置的精确恢复不在首版范围。明确的原生 Stop 入口可随控制能力增加，但不把普通自然语言消息已入库描述成取消已经执行。
