# Personal Agent 定时计划设计

状态：2026-11-06，24 项产品边界已确认，四个迭代已实现，工程检查与真实模型小样本验收通过。本文描述首版行为，[实现方案](SCHEDULE-IMPLEMENTATION.md)描述字段、事务和验收。术语见 [CONTEXT.md](../CONTEXT.md)。

## 1. 范围与入口

使用者通过主 Agent 登记目标、上下文和时间安排。每次到期创建独立 Task，拥有独立结果、工作区和执行预算；同一 Task 内继续沿用已有的多阶段执行。

调度随 Personal Agent 进程运行；进程停机时不执行，重新启动后按漏跑规则处理。

支持现有执行器能力范围内的普通目标，例如定时生成练习题；需要连续检查新增信息的计划另外维护检查区间和检查进度。登记时将这一区别说明给使用者，不能仅凭 cron 推断任务必然需要补查历史。明确要求“只看最近一天”的目标不擅自改成不限时段的连续检查。

首版包含登记、查询、修改、暂停、恢复、取消、触发历史、结果通知和背景更新建议。时间规则为五段 cron、分钟精度和独立 IANA 时区，默认 Asia/Shanghai。新登记不立即运行，首次触发严格晚于登记时刻。法定节假日和调休不能被解释为普通工作日规则。

不包含单次预约、同一 Task 的定时续跑、跨 Task 共享工作区、跨周期内容去重、逐来源进度、自动增加预算或数据库迁移。每次报告允许重复内容。

## 2. 调度与执行

~~~mermaid
flowchart LR
    U[用户消息] --> A[主 Agent 的计划工具]
    A --> S[(计划定义)]
    D[调度循环] --> S
    D --> O[(触发记录)]
    O --> T[独立 Task]
    T --> W[现有 Task worker]
    W --> C[现有任务回调]
    C --> P[(成功检查进度)]
    C --> N[结果与背景更新建议]
~~~

到期表示可以入队，真正开始仍受全局 Task 并发上限约束。首次开始是 worker 取得执行权、即将调用执行器时持久记录的边界；领取队列记录不等于开始。重启、续跑和修改单次 Task 不清除首次开始标记。

同计划自动触发不重叠。已有 Task 排队、执行或仍有能续跑的回调时，本次触发记为忙碌跳过，等待下个正常周期，不积累待执行请求。已稳定停在等待输入或预算不足的 Task 不阻止下一周期。

使用者明确续跑旧 Task 时允许与新 Task 并行，仍受全局并发上限约束。每次报告标明计划和 Task；人工续跑不会自动恢复暂停或取消的计划。

停机错过多个周期时只合并执行一次。普通目标按当前目标执行，不补造每个历史周期的任务；连续检查目标按尚未成功检查的区间补查。

## 3. 检查区间与进度

下次触发时间和成功检查进度是两个独立概念。入队、忙碌跳过、执行失败或部分结果都不能推进检查进度。

连续检查的规则如下：

1. 未另行指定起点时，首次检查从首次应触发时刻的前一个 cron 时间点开始。该起点在登记时保存，不因第一次执行迟到而丢失停机期间的信息。
2. 每次 Task 首次实际开始时，以当前成功检查终点为起点；尚无成功记录时使用首次检查起点。终点取这次首次开始时刻。区间随后冻结，续跑和重启不扩大终点。
3. 检查区间采用左闭右开形式。来源时间精度不足时允许重复读取边界内容，不以去重为由漏掉边界。
4. 任务按目标完成、结果保存且所有指定必需来源都检查完整后，在同一事务推进进度。通知失败只重试投递，不重做已经成功的检查。
5. 指定来源部分失败时可交付已有结果，但不推进进度；下个周期重新检查。网站没有历史查询能力、历史内容缺失等情况必须说明，不能冒充检查完整。
6. 成功记录只对原计划内容及对应区间有效。迟到结果不得倒退进度，也不得推进已变更目标或主动恢复后新起点的计划。
7. 部分执行耗尽预算时，不自动增加预算、缩短区间或跳过旧信息。通知使用者追加执行时间或调整范围，未来周期仍照常尝试。积压可能需要人工处理。

例如：周三 15:00 登记每天 09:00 的检查，首次基准起点为周三 09:00；周四排队到 11:00 开始，则首次检查周三 09:00 至周四 11:00。若从未成功就停机多天，原起点保留，不滑动为恢复前一天。

普通定时目标不保存检查进度，但同样保存首次开始时刻，作为本次相对时间解释的基准。

## 4. 用户操作及故障

| 操作或情况 | 后续触发 | 已创建 Task 与检查进度 |
| --- | --- | --- |
| 修改目标、来源或影响判断的背景 | 下个正常周期使用新定义 | 取消未开始的旧 Task，保留已开始的；新定义首次回看完整周期，旧积压不自动转移 |
| 仅改名称、执行时间或计划预算 | 修改时间规则时重算未来时间 | 保留检查进度；已创建 Task 保留原快照和预算 |
| 主动暂停 | 停止未来触发 | 取消未开始的 Task，保留已开始的 |
| 从主动暂停恢复 | 从未来正常周期触发 | 从恢复时刻积累新检查范围；不补暂停期间，不重启旧队列、不增加旧 Task 预算 |
| 配置无效或固定附件不可用 | 自动暂停并通知一次 | 不把尚未检查的区间记成成功 |
| 修复故障后恢复，内容未变 | 从未来正常周期触发 | 保留原检查进度，下次补查故障期间 |
| 取消计划 | 永久停止未来触发 | 取消未开始的 Task，保留已开始的及历史；计划不恢复 |
| 单次失败、等待输入或预算不足 | 不暂停计划 | 不推进检查进度；每次失败均通知 |
| 同一原因连续失败 | 继续正常周期 | 不去重失败通知，每次执行均保留结果 |
| 回复某次 Task 补充资料或追加预算 | 不自动修改未来周期的定义 | 默认仅影响本次 Task；明确说“以后每次”才修改计划 |

普通来源网站访问失败属于单次执行失败，不能因其同时是必需来源就改为计划自动暂停。“固定附件不可用”指计划绑定的材料文件已缺失、被删除或不能读取；数据库和未知程序错误按运行故障处理，不能伪装成材料问题。

恢复和修改同时发生时，主动恢复的“不补暂停期间”优先：新检查起点不早于恢复时刻。故障暂停期间改了检查内容，则按新定义首检处理。重复说“暂停”可以把故障暂停明确改为主动暂停。

自动暂停也需要使用者修复并恢复，不后台反复尝试启用。取消、暂停与首次开始的竞态以数据库事务顺序为准，不能仅通过 queued/running 状态猜测任务是否开始过。

## 5. 固定背景与背景更新建议

每次任务复制计划的目标、背景和附件，后续阶段继续读当前个人记忆。发生冲突时固定计划背景优先；没有冲突的记忆仍可提供事实和偏好，不能扩大目标。

执行时发现可能不一致，生成具体的背景更新建议，随本次结果或失败通知一起发送。例如：

> 计划 #3 当前背景：项目使用 Go。\
> 当前记忆：项目已迁移到 Rust。\
> 建议 #12：将计划背景中的“使用 Go”改为“使用 Rust”。\
> 是否同步到计划 #3？本次任务仍按原背景执行。

每条建议保留来源、原文、建议改文及对应版本。同一计划的同一变化自动提醒一次，未回复保持待处理；用户可以稍后确认或选择保留原设置，等待答复不阻塞计划。

确认仅修改建议指定的当前计划。计划或对应记忆已变化时，旧建议不能直接应用；重新展示具体差异，再由用户确认。这种对用户确认请求的过期回应，不属于每个周期重复提醒。自动提醒的变化身份与确认时的版本校验分别记录。

回复“同步”时必须能定位唯一建议；不能只凭截断的聊天历史重建改文。无法定位或同一条通知有多个建议时，要求指定建议编号。同步成功按内容修改处理，已开始 Task 不换输入。检测差异不代表新记忆一定适用于这个计划，因此不自动同步，也不扩展到其他计划。

## 6. 授权、通知与查询

计划的创建、更新、暂停、恢复、取消和建议应用，只能来自直接用户事件。Task 回调可以提交更新建议，不能应用建议或修改计划。网页、附件和自动调度事件不构成新的计划授权。

调度按已保存的授权创建内部来源事件，不能伪造用户消息。每次写操作保留用户来源、请求幂等结果与计划版本，成功提交后才回复已登记或已修改。

每次结果显示计划编号、Task 编号；检查型任务另显示实际检查区间及是否完整。成功执行与消息送达分别显示。计划自动暂停通知只在状态真正变化时生成一次；单次失败通知每次保留，不沿用背景建议去重。

查询计划展示定义、状态、下次时间、检查进度、最近执行结果及待处理建议。查询触发历史能解释忙碌跳过、合并补跑和自动暂停。旧内容的 Task 及结果仍可单独查看，不混成当前定义的进度。

## 7. 实现与交付约定

复用现有 SQLite Store、单实例锁、Task worker、用户对话、回调与 outbox。新增计划、触发记录、背景更新建议三类持久记录，不增加第二套任务执行器或系统 crontab。

使用新 schema 的独立数据库路径，保留旧库，不迁移、不清空旧数据。分阶段交付为：普通周期任务；连续检查进度；背景更新建议；工具、查询和回归集成。每个阶段都有可单独验证的边界，完整首版包括所有已确认行为。
