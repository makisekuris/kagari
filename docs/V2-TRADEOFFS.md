# V2 取舍记录

## 目标与状态

目标：逐渐实现个人 Agent，管理长期个人记忆和任务；主 Agent 能异步协调两者。每一轮设计与实现都说明动作的动机、代价和验证方式。

已明确的边界：单用户、单实例、Telegram 私聊入口；V2 不承担 V1 数据和接口的兼容要求。术语见 [CONTEXT.md](../CONTEXT.md)。

当前记录已确认的产品取舍及其实现边界。使用者已确认 `1B、2A、3A、4A、5B、6A、7A、8A`，并选择并行执行多个独立任务，将 Q9 的并发数从 2 调整为 3–4；首版按默认 4、可配置整理。运行语义见 [V2 架构与运行说明](V2-DESIGN.md)。当前 V2 schema 不保证兼容先前版本的 V2 personal 数据库；启动当前版本应指定新数据库，程序不会自动迁移或删除旧库。

## 第一轮：已确定

### 1. 自动维护使用者的稳定事实与偏好（1B）

**决定**：无需使用者每次说“记住”，Agent 可以从使用者提供的信息中识别并保存稳定事实与偏好。网页知识与任务结果不自动并入个人事实。

**动机**：减轻使用者维护记忆的负担，使不同任务能够沿用与当前工作相关的个人背景。

**代价**：模型可能误判临时信息或误解事实，因此需要可检查、纠正和删除的记忆管理。冲突处理采用 4A，遗忘范围采用 8A；异步更新流程见架构草案。

**架构影响**：个人记忆与任务材料分别存储和检索；记录记忆来自哪次使用者输入。异步维护需要明确“已提交”和“已生效”的区别，不能只提供一个文本文件就声称完成自动维护。

**待验证的体验**：使用者说明稳定偏好后，后续相关任务能采用它；网页中的人物资料不会被写成使用者的个人事实。

### 2. 在原目标范围内自主推进，新增目标时询问（2A）

**决定**：Agent 可以为达成原目标补充步骤和资料；不能因为发现一件相关的事，就自动把它作为新的长期目标继续执行。

**动机**：保留 Agent 自主完成工作的能力，避免使用者逐步指挥每一次读取或分析。

**代价**：需要判断步骤是否仍服务于原目标，并明确停止条件。目标范围、执行预算和用户调整目标的处理不能仅靠回调到达顺序决定。

**架构影响**：任务回调可能触发同一任务的下一次执行，不能一律只允许发通知。回调中的材料仍是数据；后续动作的权限必须来自使用者原先授权的任务。

**例子**：评估框架 A 是否适合某项目时，补读限制说明或必要的替代方案属于原评估。主动启动项目迁移属于新目标。

**待验证的体验**：资料不足时能在原任务内继续取得依据；执行结束后不会自行创建一个未经授权的迁移任务。

### 3. 第一轮能力为读取资料、研究分析和生成内容（3A）

**决定**：先用只读资料任务验证 personal agent 的完整协作流程。写文件、执行任意命令和修改外部服务不属于这一轮的任务工具范围。

**动机**：先观察任务关联、上下文、记忆和异步反馈是否正确，降低排查失败时需要同时考虑的变量。

**代价**：第一轮无法替使用者执行部署、修改远端数据等动作；生成的内容仍需通过回复或成果记录交付。

**范围解释**：保存本项目自己的会话、任务、记忆与成果记录属于运行所需的持久化，不是向任务开放任意外部写入权限。只读工具边界仅限定第一轮，不替代整个持续目标。

**待验证的体验**：后台读取任务运行时主对话仍可响应，个人记忆能够维护，任务完成后有明确归属的反馈。

## 第二轮：已确定

### 4. 明确纠正自动更新，含糊变化不覆盖（4A）

**决定**：使用者明确纠正个人事实时自动更新；含糊或临时的变化先不覆盖旧记忆。按 2026-11-04 确认的静默维护约定，待澄清问题保留在 Run 中，用户主动查询时再反馈。

**动机**：把稳定个人事实与当前情境分开。例如“最近项目都在用 Python”不足以自动替换“主要使用 Go”，而“我现在的主力语言改成 Rust 了”是明确变化。

**代价**：部分真实变化会晚于实际发生时间进入长期记忆，也可能需要使用者进一步说明。没有选择“任何新表述都直接覆盖旧值”。

**架构影响**：判断事实含义与校验写入版本是两件事。版本校验能防止旧异步操作覆盖新操作，不能代替对临时表述或矛盾的判断。

**待验证的体验**：临时项目情况不覆盖长期偏好；明确纠正可生效；异步旧写入不撤销更新后的事实。

### 5. 每个 Task 默认累计执行预算为 30 分钟（5B）

**决定**：一个 Task 默认累计执行 30 分钟，排队不计。达到上限仍未完成时，交付阶段结果并等待使用者选择是否继续。

**动机**：优先给 Agent 较完整的自主探索空间，减少深入任务频繁请求续跑的次数。

**代价**：单个任务可能占用后台执行能力更久，产生更高的模型与工具消耗。30 分钟是执行预算，不保证任务会完成，也不是模型费用上限。

**架构影响**：预算属于整个 Task，不能因为自动创建下一次 Run 或重启服务就重新获得 30 分钟。达到预算上限与任务成功完成是不同的状态；是否继续由使用者决定。等待使用者时不运行后台模型。

**待验证的体验**：在测试时钟下让同一 Task 跨多次执行累计到预算上限，确认不会再自动领取后续执行，且能查看阶段成果。

### 6. 任务关键节点通知，普通进度与记忆维护静默可查（6A）

**决定**：Task 完成、失败、需要使用者输入，以及有可用阶段成果时主动通知；普通进度保持静默。2026-11-04 更新：自动记忆检查异步运行，在成功、失败和需要澄清时都保持静默。用户明确要求保存、更正或遗忘时，同步提交记忆、历史与幂等请求；只有提交成功后才报告已生效，校验或版本冲突返回当前对话。

**动机**：后台任务与记忆维护会产生大量事件，主对话只呈现需要使用者关注的变化。

**代价**：记忆维护失败或需要澄清时不会打断用户，部分记忆可能因此暂未更新。执行结果、错误和记忆变更记录必须保留以供查询。

**架构影响**：自动记忆检查把结果和错误保存在 `memory_review` Run 中，不创建主对话回调或待发送消息。显式记忆变更在同一事务中写入当前值、历史和请求记录，不创建 Run；失败不保留请求记录。Task 回调仍按关键节点通知策略处理。

**待验证的体验**：自动记忆检查成功、失败或需要澄清都不主动发消息，Run 仍可查询；显式记忆操作只有事务提交后才反馈成功；Task 失败或需要补充信息时仍然能通知。

## 第三轮：已确定

### 7. 按阶段成果恢复（7A）

**决定**：保存已完成的阶段成果，中断后继续同一任务；未保存的阶段可能重做。

**动机**：保留 30 分钟任务中已经完成的工作，先把恢复建立在可检查的业务成果上。

**代价**：不保证恢复到某一次模型或工具调用的精确位置，正在执行的阶段可能产生重复读取和模型消耗。

**架构影响**：Task 与 Run 分开；阶段结果只保存摘要和来源。Store 根据执行错误和累计预算决定状态：成功进入 `awaiting_review`，失败进入 `failed`，预算耗尽时优先进入 `waiting_budget`。Run 领取时计算剩余预算，不把它单独持久化。恢复以已保存的结果为依据，不能重新执行所有已经完成的阶段，也不能给任务重置预算。

**待验证的体验**：完成阶段 A、执行阶段 B 时中断；恢复后仍可查看 A，使用它继续原目标，且剩余预算保持连续。

**Q7 的代码依据**：当前 [Analyze](../internal/agent/engine.go) 没有配置检查点存储或检查点 ID。核对本地 Eino v0.9.21 的 `adk/runner.go`，TypedRunner 在显式中断或携带中断状态的取消事件处保存检查点，并非自动保存每次模型或工具调用。7B 还需要设计可恢复边界，不能仅靠接入存储就保证任意进程崩溃后的逐步恢复。

### 8. 从长期记忆遗忘，保留聊天与任务历史（8A）

**决定**：将指定事实或偏好移出长期记忆，并阻止后台从旧记录重新提取它；保留本地聊天与任务历史。

**动机**：明确区分“不再作为个人记忆使用”和“清除历史数据”，同时保留任务与决策的来历。

**代价**：原文可能仍存在历史记录和旧任务成果中，不能将此功能描述为彻底擦除。

**架构影响**：删除当前值还不够，需要保留遗忘标记和来源边界，拒绝迟到的旧写入或重新处理旧消息时恢复该记忆。以后使用者重新明确提供的事实可以按新输入处理。

**待验证的体验**：遗忘后检索不再返回该个人记忆；重放旧消息或完成较早排队的自动记忆检查，不会让它复活。

### 9. 多个独立任务并行，首版默认上限 4（9A 调整）

**决定**：接受使用者提出的 3–4 个独立任务并发，首版默认上限设为 4，并允许配置。超出上限的任务排队；主对话与记忆维护独立运行，不占这四个任务槽。

**动机**：单实例能够运行多个独立任务。30 分钟任务不必独占后台执行能力，较晚到达的任务可以利用空闲槽。

**代价**：同时发生的模型与网络请求更多，需要处理事件交错。任务槽数量不等于模型服务的请求额度，增加并发也不保证所有任务等比例变快。

**架构影响**：不同 Task 可以并行，同一 Task 同一时刻最多一个有效 Run。领取、状态更新和事件关联需要使用稳定标识；不能让多个 Run 同时修改同一目标。

**待验证的体验**：前四个任务可以进入执行，第五个保持排队；一个槽释放后第五个开始。期间聊天和记忆维护仍可推进，结果不会串到其他任务。

## 验收场景草案

以下是未来验证所需的证据，不表示当前代码已通过。尚未决定的产品行为不使用推荐项代替预期结果。

| 场景 | 预期体验 | 为什么需要这个证据 |
| --- | --- | --- |
| 自动记忆并跨重启使用 | 使用者说出稳定偏好，没有说“记住”；后台维护后重启服务，后续相关任务仍采用该偏好，并能查到来源 | 单轮提示词里出现这句话，不能证明长期记忆已经持久化并被后续检索 |
| 个人事实与任务材料分开 | 使用者的偏好可以成为个人记忆；网页中的人物资料与临时任务内容不会自动变成使用者的事实 | 能调用写入工具，不代表模型正确选择了该记住的内容 |
| 在原目标内自主继续 | 第一次读取资料不足，主 Agent 在允许的预算内继续同一任务；发现额外迁移工作时不会自行开展 | 一次子 Agent 执行成功，不能证明任务能够跨执行持续推进，也不能证明授权边界正确 |
| 任务变更仍可追踪 | 使用者能查询、调整和取消目标；旧执行迟到时，其结果不会覆盖当前目标的状态或被当成新结果发布 | 单用户仍然存在后台事件交错，任务身份与执行身份必须能区分 |
| 后台工作不阻塞主对话 | 用可控的执行器让阅读任务保持运行；此时主对话能回答新问题，记忆维护也能完成；任务结束后结果归属明确 | 顺序调用成功或多开几个协程，不能证明两个后台通路与主对话真正独立 |

工程验证使用临时数据库、可控执行器和模拟渠道，检查持久化、事件顺序及异步处理。模型如何识别稳定事实、是否选择继续任务，还需要真实模型的小样本观察；模拟模型按脚本调用工具的测试不证明这些判断已经可靠。

## 当前实现语义

- Task 阶段成功、失败和预算耗尽后的状态由 Store 决定；`StageResult` 仅包含摘要与来源，不通过模型结果中的状态字段决定任务状态。
- 自动记忆 review 是静默 `memory_review` Run；显式 `memory_put`、`memory_forget` 同步写入，不创建 Run。
- Task Run 的 `RemainingMS` 在 `ClaimRun` 时从 Task 累计预算计算，不写入数据库或 JSON。
- 当前 V2 schema 不迁移先前版本的 V2 personal 数据库。部署当前版本时应指定新数据库；旧库由使用者保管，程序不会自动删除。

## 微信渠道设计访谈（2026-11-04，尚未实现）

以下记录已确认的设计方向，不表示当前实现已具备这些能力。

### 已确认

- **1A：每个实例只启用一个通信渠道**，可配置为 Telegram 或微信。沿用单使用者、单实例的产品边界。
- **2A：通过 CLI 绑定微信**。登录流程展示二维码和备用链接，支持保存二维码图片，扫码授权成功后保存凭证。
- **4A：切换渠道后接续同一份对话和任务**。长期记忆、对话历史和任务均可继续使用；切换渠道只改变交互入口。
- **5A：不同微信账号需要显式换绑**。同一账号可以重新授权；新账号扫码成功不能自动替换原绑定并获得已有个人数据的访问权。
- **6A：附件保存到明确删除为止**。原文件保存在本地，供任务恢复和后续引用；不因任务完成而自动清理，磁盘占用会随文件积累而增长。
- **7A：未发出的结果送到当前启用的渠道**。任务从哪个渠道提交不限定最终交付渠道；已经成功发送的消息不补发，发送结果不确定的消息不自动转投。
- **8A：登录失效不停止已接收任务**。任务按原预算继续，结果保存在本地；恢复登录且满足渠道发送条件后再投递。服务状态和日志提示需要重新登录。
- **9A：Telegram 同步支持文件收发**。两个适配器均接入统一消息协议，支持文字和文件；文件传输能力与 Agent 的解析、生成能力保持独立。
- **10A：首版只接入文字和普通文件消息**。PDF、文档、压缩包等按原文件收发；图片可通过普通文件消息进入，不接入原生相册图片、语音和视频消息。
- **11A：主 Agent 选择交付文件**。按任务要求将明确的成果文件与回复文字一起加入发送队列；任务阶段写过的所有文件不自动成为交付物。
- **12A：通过 CLI 删除附件**。按附件 ID 删除指定的附件原文件；消息记录保留附件已删除的状态，历史分析结果和个人记忆仍保留。
- **13A：单文件收发统一上限为 20 MB（20,000,000 字节）**。超过本地上限时明确报告；微信平台实际允许的大小仍需联调，不把本地上限当成平台保证。
- **14A：通过配置和重启切换渠道**。使用同一数据库和文件目录，任务按现有恢复机制继续，执行中的阶段可能重做。同一账号重新授权不要求重启整个服务。
- **使用者与渠道账号分开**。通信渠道只是同一使用者与主 Agent 交互的入口；切换渠道后仍可复用同一份个人记忆。
- **统一消息协议**。渠道消息转换成共同的输入交给主 Agent，正文与附件保留关联。渠道的收发协议不决定个人记忆的归属。
- **文件收发与文件处理分开**。适配层接收和发送附件，文件事件及相关用户信息交给 Agent；文件内容如何读取、解析或生成属于后续 Agent 能力。

### 对“迁移”的澄清

此前 Q3 把旧数据库结构兼容与个人记忆归属混为一谈，原来的 A/B 选项不作为已确认决定。使用者已明确：长期记忆应与通信渠道解耦，可以跨渠道复用。

当前 `personal_memories` 不包含渠道字段，但启动入口把 Telegram 用户 ID 作为 owner，收件进度、消息 ID 和发送回执也采用现有 Telegram 路径的表示。统一消息协议需要处理这些身份与收发契约；它不要求按渠道复制或重建个人记忆。

后续若调整旧消息记录的存储结构，需要单独确定旧数据的兼容方式。个人记忆仍保留对来源事件的引用，结构调整时需要保留这条溯源关系。

### 平台事实（2026-11-04 核对）

- Telegram 托管 Bot API 的 `getFile` 下载上限为 20 MB，`sendDocument` 上传上限为 50 MB。两者不是同一个限额，统一的本地收发上限属于 Kagari 的产品选择。来源：[getFile](https://core.telegram.org/bots/api#getfile)、[sendDocument](https://core.telegram.org/bots/api#senddocument)。
- 腾讯微信插件的公开协议说明了普通文件的收发格式，但没有明确平台的文件大小上限，也没有明确 `context_token` 的有效期。重新扫码返回登录凭证，不能据此保证恢复旧会话的发送能力。来源：[微信后端协议](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol_zh_CN.md)。
- 微信会话恢复和实际文件限制需要真实账号联调；不能用插件内部限额或模拟接口测试代替平台结论。

### 实施建议（待整体方案确认）

- 分开发送的文字与文件保留原始消息边界、顺序和引用关系，统一交给主 Agent 判断任务关联；不由适配层根据时间间隔猜测哪些消息应拼接。文件单独到达也构成有效输入。
- 复用 Task 工作目录与文件成果接口。入站附件引用随任务输入传递，出站仅交付主 Agent 明确选择的文件；进入发送队列时固定该文件的内容，避免后续修改改变待发送成果。
- 对本次改动前的现有 V2 数据库采用增量升级，保留任务、对话、记忆及来源事件关系。未知旧结构应明确报告不兼容，不自动替换为空数据库。
- 重新授权后仍不能发送的结果继续保留。若需要新的会话上下文，应提示使用者向 Bot 发起新消息，取得可用上下文后再尝试投递；不能把登录成功视为已送达。

### 访谈收敛

产品取舍已收敛为上述选择。统一协议、模块职责、CLI 流程、数据兼容和验收场景见 [多渠道消息与附件设计](CHANNEL-DESIGN.md)。该方案包含实现建议，等待使用者确认整体理解；当前尚未实现渠道改造。
