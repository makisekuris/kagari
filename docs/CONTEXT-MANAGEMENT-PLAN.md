## 1. 目标与范围

完成改造后，应能回答四个问题：本次执行依据了哪些要求与材料；省略的内容从哪里继续读取；前几个阶段已经确认了什么；新要求与新反馈是否已经被处理。

本轮包括：

- 主对话、Task Run、任务回调三种用途的上下文组装。
- 历史消息、Run 结果、来源、文本附件和工作区文件的有界读取。
- 个人记忆的相关性选择、来源版本和当前有效状态。
- 跨 Run 的累计进展、失败尝试、产物引用与反馈记录。
- 单个模型循环中的上下文压缩，以及新输入在阶段边界的交接。
- 沿用现有 trace 的排查能力和对应回归验证。

多模态解析、subagent 调度、skill 加载与自迭代不在本轮实现。后续接入这些能力时，使用这里的材料引用、执行输入和成果交接规则。也不引入向量数据库、图数据库、外部消息系统或新的通用 Agent 框架。

## 2. 改造前实现与依据

| 改造前实现 | 需要解决的问题 |
| --- | --- |
| `Runtime.context` 取最近的历史、Task 和 Memory；`boundedTurnInput` 再次截断 | 选择规则分散；当前任务的重要信息可能被无关的近期内容挤掉 |
| `get_run` 和 `list_runs` 返回完整 Run | 输入入口有长度限制，工具读取却可能一次加入大量内容 |
| `read_attachment`、`read_file` 可一次返回最多 1 MiB 文本；`ls` 返回完整目录 | 文件大小限制不能代替模型单次读取限制 |
| `Run.Input` 冻结任务输入，执行器另外加载当前记忆 | 保存的输入不能完整解释实际采用的个人背景；提示词又要求主 Agent 把记忆复制进 Context |
| `FinishStage` 用本次结果替换 checkpoint，`ContinueTask` 将其放入 Previous | 程序没有维护累计进展的明确规则；历史约束和失败原因依赖模型继续复述 |
| 完整来源保存在完成阶段的 `Run.Result`；工作区跨阶段保留 | 主 Agent 与执行器的回查能力不对称；工作区路径不能代表固定版本的产物 |
| 现有日志记录模型输入、输出与 usage，但有轮转和保留期限 | 可用于排查，不能作为持久的任务材料存储或恢复协议 |

## 3. 共同的数据规则

### 3.1 信息的职责

| 信息 | 保存位置与职责 |
| --- | --- |
| 任务要求 | Task 的 Goal、Context；来源是使用者授权的请求 |
| 累计进展 | Task 的结构化 checkpoint；记录已报告的进展、未解决问题及证据；不自动代表经过独立验证 |
| 执行记录 | Run.Input、Run.Result、来源与不可变附件；保留各阶段当时的输入和结果 |
| 本次上下文 | 从上述记录中选择并组装的模型输入；可因用途和长度限制不同而变化 |
| 个人记忆 | 现有 Memory；只表达使用者的稳定事实与偏好 |

Task 的要求不从工具输出、历史摘要或压缩摘要中反向恢复。Run 完成不会直接完成 Task；继续由主 Agent 在回调中调用 continue_task 或 settle_task 作出决定。迭代五增加已登记输入的并发检查，不增加逐项内容验收。

### 3.2 引用和读取

引用复用现有业务 ID：消息分别使用 event/history ID；来源的 source_id 使用全局唯一 material ID，附 run_id 表明出处；附件使用 attachment ID；工作区文件使用 `(task_id, relative_path)` 加内容版本。相同 URL 的不同浏览器观察仍是不同来源，不能按 URL 合并。

所有模型可见的长内容遵循同一规则：返回有效的结构、内容摘要或分页片段、原始长度、是否省略、下一页入口。结构化内容先裁剪字段或分页集合，再序列化；禁止截断序列化后的 JSON 字符串。

文本分页按 Unicode 码点计数，列表按条目计数。首版默认每页 4,000 码点、最多 8,000；列表默认 20 项、最多 50 项。它们是初始工程上限，验收后可统一调整，不为每个工具增加一套配置。引用自身保持完整，不截断 ID 或文件路径。

完整工具返回另受 32 KiB JSON 上限约束；接入容量规则后还不得超过输入上限 H 的四分之一字节预算。先减少文本或条目，再序列化检查，按实际返回内容计算下一页。码点 limit 不保证读满，单工具上限也不替代整次模型输入检查。

分页只承诺读取已保存或已采集的内容。若 HTTP 提取或浏览器观察本身已截断，仍返回原有 truncated 状态；重新获取网页会产生新的观察，不能称为恢复了同一份原文。

来源引用同时返回采集时间，旧引用不会自动替换成最新网页内容。执行器根据任务对时效的要求显式重新采集；新旧观察分别保存。任务完成后材料随历史保留，首版不做定期清理。已经持久保存的不可变附件复用原引用和删除检查，不为同一正文额外建立一个可绕过附件状态的入口。

工作区文件可变，分页结果携带内容版本标记；读取下一页时校验该标记，内容变化则要求重新从首页读取。需要确认固定版本的交付物时使用不可变附件 ID；工作区路径用于继续编辑和排查。

### 3.3 权限与有效性

- 主 Agent 可读取该使用者的记录；任务回调写操作仍只针对所属 Task。
- 执行器可读取所属 Task 的历史 Run、工作区和主 Agent 明确关联的材料。跨 Task 关联只授予指定旧 Run 结果或附件的读取范围，不能沿关联自动扩大到旧 Task 的全部历史和其他材料；读取工具在服务端检查。
- 当前 Task revision、取消状态和附件可用性仍由 Store 与工具检查。上下文快照不会延长已经失效的权限。
- 每次组装上下文时排除已经遗忘的 Memory；历史原文的保留与附件删除继续遵循现有定义。不把历史回查结果重新解释成当前个人偏好。
- 累计执行时长和同一 Task 串行执行的规则保持有效。压缩调用的耗时也计入原有 Run 或回调时长。

## 4. 迭代一 有界读取与证据回查

交付结果：采集到的材料在阶段结束前就能持久回查；主 Agent 和执行器按需读取，每次工具返回有明确上限。材料保存与引用索引的契约需在本迭代固定，不再预先承诺此迭代完全不涉及 schema。

### 改动

1. `list_runs` 返回 Run 摘要和分页入口；`get_run` 默认返回结构化详情摘要与材料索引，不直接返回整段 Input/Result。Store 的 `Run`、`Runs` 保留完整内部数据，模型侧单独构造读取结果，诊断命令继续使用内部记录。
2. 增加按 Run 读取 input/result 文本片段和来源正文的工具；来源通过 material ID 定位并在服务端检查 Run 归属。执行器能读取本 Task 的旧 Run；对主 Agent 明确关联的其他 Task 的已终止 Run，只读取被授权的结果与证据。
3. 每次采集到来源或不可再生成的工具材料后，先保存正文及引用，再向模型返回成功结果。session 可保留缓存，持久读取通过 Store 提供；`internal/agent` 使用注入的保存与读取能力，不依赖 `internal/personal`。阶段结束保存的 Run.Result 引用这些已保存材料。落盘失败不能伪装成已有可恢复证据；同一 Run 在重启后重采集时生成新观察 ID，不能覆盖此前观察。
4. 给 `read_attachment`、`read_file`、`ls` 增加分页参数，保留现有文件大小、UTF-8 校验、工作区路径约束和删除检查。省略分页参数也返回有界首页。提示词明确区分片段和全文；局部修改优先使用现有 `edit_file`，完整覆盖前应读取完整文件，避免把未读部分误当作不存在。
5. `read_url`、`browse_url` 默认返回来源摘要与正文首页；后续读取已经采集的来源不再次消耗网络读取次数，也不改变浏览器状态。浏览器交互仍只能使用当前快照的有效引用。
6. 主 Agent 增加 Task 工作区的只读目录和文件入口，复用现有 Workspace 路径边界。查看不存在的工作区不得顺带创建目录。消息历史也提供按 ID 回查入口，使被截断的当前消息、回复消息可以展开。
7. 补充历史 Task 的关键词、时间条件和分页查询。当前 list_tasks 只返回最近 50 条，get_task 要求已知 ID；只有内容续读不能找到用户口中的旧任务。候选仍歧义时由主 Agent 澄清，再作材料关联。
8. 已保存文本提供有界的关键词定位及片段读取，避免对定位类任务逐页扫描。任务明确要求全文阅读时，由执行器用 checkpoint_reading 提交续读位置和已提取要点，跨阶段继续；工具返回一页不自动推进持久位置。网络读取次数、工具往返次数和已覆盖文本范围分别记录，不能因为读到几页就声称读过全文。

### 调用链与兼容

`personalTools / attachmentTools / workspace.Tools → 分页结果 → 模型`；`readingSession → 来源摘要 → 当前来源续读`；`TaskExecutor → 本 Task 历史来源读取`。

修改工具 schema、提示词和模拟模型 fixture，取消“get_run 总会返回全文”的假设。新增来源正文进入 SQLite 材料表，StageResult 改为持久引用；附件继续留在现有存储。保留旧工具名称，新增参数为可选参数；完整 Store 查询继续可用，CLI 导出通过 Store 显式展开来源，不再假设 Run.Result 内嵌正文。

### 验收

- 1 MiB 合法文本、长 Run 结果、大目录不会通过一次调用全部进入模型；末页、空内容、越界参数和多字节字符均有确定结果。
- 重启后，执行器能从同一 Task 的早期 Run 找回来源；未显式关联的跨 Task 读取被拒绝。
- 阶段尚未结束时中断，已成功保存的材料仍可读取；没有完成保存的内容不返回持久引用。
- 显式关联旧 Run 或附件后允许指定范围读取；未关联的旧任务材料及传递关联被拒绝。
- 分页中途修改工作区文件能检测版本变化；删除附件后续读失败，不从缓存返回原件。
- 动态页面相同 URL 的多次观察能分别读取；对已截断的采集内容不会承诺可恢复全文。
- 超出最近任务列表范围的旧 Task 能经关键词或时间找到；需要全文阅读但超过单阶段轮数时，保存续读位置，不将片段当作全文。

## 5. 迭代二 统一组装与来源记录

交付结果：任务关联和用途决定上下文内容；只在一处做最终长度分配；能检查一次 Run 实际采用了哪些来源和记忆版本。

### 改动

在 `internal/personal` 内按职责组织上下文选择和渲染，保留三个明确入口，不引入可插拔的通用 ContextEngine：

| 用途 | 固定优先级 |
| --- | --- |
| 主对话 | 当前请求及来源 → 明确回复的消息与 Task → 待处理变化 → 必要的近期交流 → 其他任务与记忆摘要 |
| Task 执行 | Goal、约束和本阶段指令 → 累计进展与未解决问题 → 新材料和相关证据 → 关联的当前有效记忆 |
| 阶段验收 | Task 当前要求 → 当前 Run 结果与产物引用 → 累计进展 → 未满足条件与用户反馈 |

本迭代先接入现有 Goal、Context、Previous 和 checkpoint；结构化累计进展在迭代三加入后再接入相应位置。本轮不新增强制验收条件。

先按用途选择，再分配长度。当前要求、revision、控制状态和引用入口不会被静默截断。必要输入自身超过上限时，明确返回无法组装的原因；不能删掉约束后继续执行。历史材料允许使用摘要和续读入口。

主 Agent 可用现有 `memory_search` 选择相关 key，创建或修改 Task 时保存 `memory_refs`。执行器在实际开始时读取这些 key 的当前有效版本，并记录实际使用的版本；新阶段会重新检查，已遗忘项不再注入。缺少引用时不自动把最近一批记忆全量补进 Task。执行器仍可按需只读搜索有效记忆，首次使用的新 key 记录当时版本，已选 key 遵循本 Run 的版本规则。普通对话仍可使用小规模记忆摘要与按需搜索。

一个阶段内保留所选记忆版本；阶段期间发生的更正在下一阶段重新选择时生效，任务要求的即时修改仍走 revision 流程。遗忘单独处理：每次模型请求前检查已注入记忆的有效状态，移除已遗忘的记忆块，并在 trace 记录省略原因。已生成的分析和历史原文不因此被全文清除。

同一条用户消息里的任务约束直接进入 Goal/Context，不等待异步 Memory Review。主 Agent 未预选的 key 在执行器第一次查到时固定版本；同一 Run 后续读取同一 key 使用固定版本并检查遗忘状态。下一 Run 重新选择。这些规则用于落实“按需查询”与“Run 内固定版本”两项已确认决定。

同步去掉提示词中“将当前记忆自由复制到 Task.Context”的要求。用户对当前任务明确提出的约束仍写入 Task.Context，即使它也曾是某条个人偏好；来源区分为任务请求与记忆引用。

### 数据约定

- Task 和 `TaskInput` 增加可选的记忆引用，创建、修改和继续执行时一致传递，Store 校验引用可读取；Goal、Context、Step 和附件引用继续表达本阶段冻结的任务输入。
- Run 增加上下文来源记录，至少包含：格式版本、task revision、来源 ID 与版本、选择原因、实际加入的长度、省略原因、组装时间。来源记录在模型调用前保存，失败则不启动本次执行。
- 来源记录不复制一份长期有效的个人记忆正文。原始模型调用仍用现有日志排查；该记录用于解释选择，不承诺在遗忘、删除或外部材料变化后逐字重放旧请求。
- 主对话和回调使用相同结构写入现有 trace；先不新增一套对话快照表。运行中的工具读取和后续裁剪也写 trace，避免把启动输入误称为整个 Run 看过的全部内容。

收拢 `Runtime.context`、`boundedTurnInput`、`readingSubmission` 的重叠选择和裁剪逻辑，保留必要的入口校验。输出同样的信息不再先后经历多种不可见的截断。

### 验收

- 大量近期无关消息不会挤掉当前 Task 的被回复消息、目标和执行指令。
- 入队后更正或遗忘的记忆，在实际开始时使用新版本或省略；trace 可解释结果。
- 运行期间遗忘记忆后，后续模型请求不再携带原有记忆块；已生成分析仍按任务材料处理。
- 任务明确约束与个人偏好冲突时，执行器遵循任务要求，并保留各自来源。
- 同一份输入的选择顺序和裁剪结果可用固定 fixture 验证；引用、JSON 结构和当前事件身份保持完整。

## 6. 迭代三 累计进展与证据交接

交付结果：执行器提交阶段增量，后续 Run 从已保存的累计进展继续；主 Agent 沿用现有工具和完成规则，并可纠正进展。

### 数据约定

结构化进展使用追加写入的 `personal_progress` 保存每个条目的版本、revision 和证据；Task.checkpoint 继续用于有界阶段交接，Run.Result 保存阶段原始结果。最小字段如下：

| 内容 | 必需信息 |
| --- | --- |
| 进展条目 | 条目 ID、说明、来源 Run 和证据引用；区分已报告成果与尚未解决的问题 |
| 失败尝试或被替代结论 | 原说明、原因、来源 Run、替代条目或重新检查条件 |
| 产物 | 不可变附件 ID 或 Run 中的文本结果引用；工作区路径只作为编辑位置 |
| 更新依据 | task revision、最近一次已应用进展的 Run ID、格式版本 |

省略某个旧条目不表示删除；通过明确的更新或替代关系改变它。当前上下文只展开仍相关的条目，历史记录可分页查阅。不增加以 verified 状态作为完成条件的检查。

### 提交与交接流程

`执行器提交阶段增量 → FinishStage 原子保存 Run.Result 与累计进展 → 主 Agent 决定继续或结束，必要时纠正进展 → 下一 Run 读取累计进展`。进展保存不依赖主 Agent 的回调完成。

执行器使用工具提交结构化进展，最终回复仍可为文字；不要求把工具调用与严格 JSON 最终输出同时发给模型端点。未提交结构化进展时仍保留普通阶段结果，不能假装已更新累计进展。进展明确标记为模型报告，程序不将它提升为已经独立验证的事实。

累计 checkpoint 不能被最新阶段摘要整体替换而无声丢失早期进展。FinishStage 在同一事务内保存结果和可用增量，并校验 task revision、来源 Run 与证据归属。重复提交不能重复应用，旧 Run 不能覆盖新进展。主 Agent 的纠正保留来源和预期进展版本，不能用旧快照整体覆盖较新的内容。

失败阶段已保存的证据和明确报告的部分成果可以保留，错误原因和未完成事项一起进入交接；不能仅凭 Run 状态把整个阶段目标标记为完成。模型进程被直接终止而未返回的进展不冒充已经提交，已采集材料仍按迭代一的规则可读。

Task 完成继续使用现有 settle_task 规则，不增加证据数量或逐项验收门槛。主 Agent 在上下文中获得阶段成果、未解决问题和证据，以便作出原有决定。文本型任务可以引用 Run 结果，不强迫每个任务生成附件或等待人工确认。

用户修改目标或约束后增加 Task revision。旧进展和证据保留原 revision，必须先判断是否仍适用于新要求，不能直接当成新目标已完成的依据。失败、取消或时长耗尽保留已经保存的材料与部分成果。

### 验收

- 三阶段任务中，第一阶段的有效结论和失败原因在第三阶段仍可定位，不依赖第二阶段完整复述。
- 主 Agent 能看到成果的原始证据和未解决事项，不把进展记录本身描述为独立验收结果。
- 产物被新附件替代后，进展引用明确指向各自版本，不默认为同一份内容。
- revision 变化、旧回调重放、进展更新失败时，累计进展与 Task 状态保持一致。

## 7. 迭代四 运行内上下文压缩

交付结果：一次 Run 或主对话中的多轮工具调用可以在受控输入长度内继续，同时保留必要要求和可回查的记录。

项目当前固定使用 Eino `v0.9.21`，已安装的 typed reduction 和 summarization middleware 可作为接入基础。实现时适配现有 `AgenticMessage`，不先升级依赖或另写一套摘要循环。

### 处理顺序

1. 每次调用模型前统计系统提示、工具 schema、消息和工具结果，不能只统计用户文本。
2. 优先把早期大工具结果替换为有界摘要及引用，保留近期完整的工具调用与返回配对。
3. 仍超过目标长度时生成运行摘要，保留当前目标、已作决定、有效进展、失败原因、待读取引用和下一步。任务要求从规范字段重新加入，不依赖摘要复述。
4. 校验摘要可用后才替换模型窗口中的旧内容。原始记录保留，压缩摘要不直接覆盖 Task 的累计进展。

先用现有事件、Run、迭代一保存的材料和附件引用恢复内容。无法从这些记录恢复的工具参数与结果，保存到同一 SQLite 材料表的 tool_record，按 event/run 隔离，再返回读取入口；不能放在模型可编辑的普通工作区。只有已经保存且有读取入口的内容才允许从窗口移除。附件和记忆使用带有效性检查的引用，不复制正文形成另一个可绕过删除的入口。

模型窗口容量由新增 model.context_window 明确提供，不从任意模型别名推断。实现方案固定了输出额度、安全余量、80% 触发和 60% 目标的计算规则；部署时填写实际端点容量，不使用中间件默认的 160,000 token 阈值。首版按实际请求文本及 schema 的 UTF-8 字节数保守估算并记录口径，以实际 usage 检查偏差，不自动放宽阈值，也不将“字符数除以四”视为中文输入的可靠上限。硬检查在迭代二接入所有模型入口，摘要能力在本迭代加入。

压缩失败时不覆盖原记录。仍在允许长度内则保留原上下文继续；已经无法安全发起请求时，结束当前阶段并保存可用成果及具体原因，避免反复提交同一个超长请求。重启仍将有效的 running Run 重新排队并重新执行阶段，不恢复模型内部执行位置。保存材料不等于工具执行恰好一次：主对话的 Task/Memory 写操作沿用现有恢复保护；任务执行器恢复后先读取已有文件和材料，再决定下一步，不由框架重放工具调用记录。

### 验收

- 连续读取长材料后触发压缩，来源仍可展开，目标和约束不变。
- 工具调用及其结果保持合法配对，未完成调用和最近结果不被割裂。
- 压缩模型报错、超时、输出空摘要时，原记录保留，调用次数有界。
- 主对话已经提交的 Task/Memory 操作不会因压缩或恢复重复执行。
- 同一组真实模型样本比较完成质量、输入 token、额外读取次数和延迟，不以压缩比例作为唯一指标。

## 8. 迭代五 阶段间新增输入交接

交付结果：用户向现有 Task 补充材料或反馈后，系统能说明它尚未处理、分配给哪个 Run、是否已处理。本迭代只在阶段边界交接，不实现运行中抢占和全渠道订阅。

### 数据与处理

复用现有 Event 原文，增加 Task 与输入事件的关联记录，包含 `task_id`、`event_id`、输入类别、顺序、分配的 Run 和处理状态。同一个 `(task_id, event_id)` 不重复登记。主 Agent 仅对明确关联的任务登记输入，不凭内容相似度把消息直通任意执行器。

材料和验收反馈进入待处理记录；目标、约束变化继续走 `ReviseTask`；取消继续走现有取消流程，不等下一个阶段。新 revision 的 Run 能看到这次变更来源，旧 Run 的迟到结果继续被拒绝。

状态分为 pending、assigned、applied：构造并保存 Run 上下文时分配输入；匹配 revision 的阶段成功保存处理结果后，才记录已处理的输入 ID。模型只是看过输入不等于已经完成处理，未处理项仍保留。

输入登记与 Task 完成通过 Store 事务确定先后。settle_task 请求 completed 时，在更新状态的同一事务中检查该 Task 已登记的 pending 和 assigned 输入；存在未处理项则拒绝本次完成，保持原状态，并返回有界的待处理输入列表供主 Agent 继续安排。不能仅在模型生成决定前检查一次，也不能把 assigned 当作已处理。这项检查不判断内容质量，不改变取消、等待输入或时长耗尽的处理规则。

若完成事务先提交，之后登记的新反馈保留为新的用户输入，不撤销之前的完成结果；由该用户事件按现有授权流程决定是否继续原 Task。已取消的 Task 不因新反馈自动恢复。

运行失败或中断时，未提交处理结果的输入重新成为待处理项；已取消 Task 不因此被自动唤醒。重新分配输入不等于重放旧工具调用，继续遵循现有恢复和幂等规则。该机制保证输入记录不丢失，不承诺任意外部副作用恰好执行一次。

### 验收

- 任务运行中补充的材料进入下阶段，重复事件不会重复登记。
- 在分配前、模型调用前和结果保存前中断，输入状态都能按记录解释并恢复。
- 用户修改要求后，旧 Run 不能消费新 revision 的输入或完成新目标。
- 输入登记先提交时，pending 或 assigned 均阻止 completed；拒绝完成不会改变 Task 状态，返回的输入仍可读取。
- 完成事务先提交时，随后登记的新反馈仍被保存，原完成结果保留，由该用户事件决定后续动作。
- 所有已登记输入处理后可以完成；取消和时长耗尽不被这项检查阻塞，跨 Task 输入被拒绝。

## 9. 文件职责与实施顺序

以下是职责划分，不预先创建所有文件。实现某个迭代时再按实际代码量拆分。

| 范围 | 改动位置 |
| --- | --- |
| 分页与材料读取 | `personal/tools.go` 拆出查询职责；`attachment_tools.go`；`workspace/tools.go`；`agent/session.go` |
| 上下文选择与渲染 | `personal/context.go` 等小文件；收拢 `runtime_conversation.go`、`model.go`、`model_result.go`、`executor.go` |
| 来源记录和累计进展 | `types.go`、`store_tasks.go`；按职责拆出 Store 方法及 schema；`inspection.go` 与现有 trace |
| 运行内压缩 | `agent` 内的模型调用配置；`personal/model.go`；现有 logging；必要的只读存储和读取工具 |
| 新输入交接 | `store_events.go`、`store_tasks.go`、`runtime_tasks.go` 与对应工具 |
| 调用方和文档 | `cmd/kagari/personal.go`、配置及示例、两类提示词、README、V2 运行说明 |

每个迭代先由主 Agent 固定共享类型、工具 schema、事务规则和验收用例，再按届时有效的 AGENTS.md 分配独立编码任务和选择模型思考强度；例如分页文件工具和固定接口后的读取工具可以分别实现。主 Agent 负责 Store 状态事务、共享文件集成和最终验证。不得让多个 Agent 同时修改 types、store_tasks 或 engine 等共享文件。

### 与定时计划的集成

[定时计划设计](SCHEDULE-DESIGN.md)和[实现方案](SCHEDULE-IMPLEMENTATION.md)正在并行落地。两项改造都涉及 TaskInput、Task 入队、revision 和数据库版本，应由同一集成者维护。

上下文组装保留调度器提供的计划来源和固定检查区间，不把它们重新解释成“当前时间”。不同周期的 Task 继续独立，不自动继承上一周期的累计进展或工作区。任务完成和结果保存的事务应与调度计划推进检查进度的规则一致，消息送达单独处理。

执行器使用 BeginScheduledRun 返回的最新 Run.Input。定时连续检查的专用 CheckAssessment 完成条件保持有效，本轮不增加通用验收门槛不等于撤销已经确定的计划检查规则。

持久化变更沿用当前定时计划已记录的新库方案：明确支持的 schema 和新库路径，保留旧库及其工作区，拒绝写入不兼容旧库，不实现迁移或自动清理。迭代一增加材料、关联和续读表，明确改变 schema。版本在集成时统一分配，不覆盖并行定时改造的版本；未实施的迭代不预建表。

## 10. 验证与交付标准

先用现有测试 fixture 记录基线，再随每个迭代补必要行为用例。测试优先覆盖引用可达、状态事务和失败恢复，避免只断言提示词措辞。

固定保留六组端到端场景：

1. 长文本附件跨页读取，早期证据在重启后仍能回查。
2. 多任务与大量无关聊天并存，当前任务要求仍完整。
3. Task 排队期间个人记忆更正或遗忘，实际输入正确。
4. 三阶段任务保留有效进展，并明确记录被推翻的结论和替代依据。
5. 新材料或约束在运行期间到达，revision 与输入状态正确。
6. 工具结果触发压缩，压缩失败或进程中断后仍能读取已保存材料；主对话不重放已提交的 Task/Memory 写操作，执行器重新执行阶段前可检查既有成果。

按改动范围运行 `go test ./internal/personal ./internal/agent ./internal/workspace ./internal/config`；涉及状态并发时对 personal 跑 race 检查；集成完成后运行项目要求的完整检查。真实模型测试沿用现有 live-eval 入口，按所改行为选择样本，不默认调用所有外部服务。

记录每组场景的结果正确性、关键引用可读取情况、模型输入用量、重复读取次数、压缩次数与失败原因。最终验收以要求和证据正确、任务能继续为先；token 与耗时必须实测后比较，不预先承诺节省比例。

实现按上述五个迭代接入同一 `context-feat` 分支。各迭代的代码入口和验收证据见实现方案末尾。
