# V2 观测性

## 使用

`make run` 启动 V2 时先打开日志文件，再启动 Telegram 轮询和工作协程。终端显示操作、关联 ID、状态和耗时；完整调用内容保存在 JSONL 文件中。V1 独有流程沿用原日志行为。

```yaml
logging:
  directory: ""       # 空值按数据库路径推导：data/kagari.db → data/kagari.logs
  rotate_mib: 50
  max_total_mib: 1024
  retention_days: 7
```

环境变量分别为 `KAGARI_LOGGING_DIRECTORY`、`KAGARI_LOGGING_ROTATE_MIB`、`KAGARI_LOGGING_MAX_TOTAL_MIB`、`KAGARI_LOGGING_RETENTION_DAYS`。V2 的 `log_level` 调整终端阈值，文件始终保留 info 及以上记录。

```sh
./bin/kagari -config config.yaml events --limit 20
./bin/kagari -config config.yaml trace --event 42
./bin/kagari -config config.yaml trace --task 3 --full
```

`events` 不显示聊天正文。`trace` 输出 JSON，包含 `state`、`state_read_at`、`records` 和 `warnings`；默认隐藏调用正文，`--full` 包含正文。查询在一个只读事务中读取当前状态，释放事务后逐条扫描日志，不把整个保留窗口装进内存。数据库不存在时返回错误，不创建数据库、初始化 schema、修改权限或触发恢复。

`state` 包含关联事件、Task、Run、投递，以及这些事件曾修改的记忆键的当前值和版本（包括已遗忘的标记）。当前记忆可能已经被后来的事件更正；原调用内容仍以历史日志为准。

`trace --task` 保留该任务与来源对话的记录；同一对话创建的其他任务有独立的 Task / Run ID，不会混入。`trace --event` 包含该事件关联的所有任务。两种查询均附带同一数据库的服务、Telegram 轮询和启动恢复记录；这些全局记录不替代事件或任务自身的历史。

## 记录与关联

每条记录包含 `schema_version`、UTC `timestamp`、`store_id`、`instance_id`、进程内递增 `seq`、`level` 和 `msg`。业务记录附 `event_id`、`task_id`、`run_id`、`delivery_id` 中适用的字段；模型和工具还附调用 ID。数据库在 `personal_meta` 保存独立 `store_id`，重新创建数据库不会把旧日志中的相同整数 ID 当作新事件。

| 范围 | 记录内容与语义 |
| --- | --- |
| 服务与轮询 | 启动、恢复计数、就绪、退出、工作协程错误；Telegram 首次成功、失败与恢复，空轮询不刷屏 |
| Telegram 输入 | 接受、过滤或去重结果；新接受的消息关联消息 ID、update ID 和 event ID |
| 主对话 | 事件输入、开始、完成、回退回复和错误；回复提交后才记录入队 |
| 模型调用 | 调用前记录应用层消息、工具定义及模型配置；结束后记录完整响应、耗时和服务实际返回的用量，缺失用量不估算 |
| 工具调用 | 工具名、调用 ID、参数、输出；Go 错误与 `ok:false` 等业务失败分开识别；`read_url` / `browse_url` 按 `Source.Usable()` 判断材料是否可用 |
| Task / Run | 目标变更、排队、执行、结束、取消、续跑、重放、无变化和过期结果；结果来自提交后的业务状态 |
| 记忆 | 同步写入与重放、后台 review 的提议/应用/跳过/冲突数量及结果 |
| 投递 | 每次发送的内容、尝试次数、远端接收凭据、重试/失败/不确定结果与本地保存结果 |

完整内容集中在 `payload`。模型记录来自 Eino 的应用层回调，不等同于最终 HTTP 请求/响应原文。主对话格式整理、后台阅读和记忆 review 使用各自的 `phase`；流式响应消费独立副本，不增加模型请求。

`delivery.remote_accepted` 仅说明 Telegram 返回了消息凭据；后续本地提交失败仍会单独记录。`store.outcome` 在事务提交成功后写出，不把重放、无变化、过期结果或冲突记作新操作成功。投递最多尝试 3 次，包含首次尝试；每个新 outbox 行从零计数。不确定是否发送成功的消息不自动重发。

## 保存与故障边界

日志目录为 0700，文件为 0600。使用专用目录；启动时会收紧目录权限。文件按约 50 MiB 轮转；单条大记录保持完整，可超过轮转目标，但不能超过总容量限制。超过总容量的单条记录会丢弃并报告，不静默截断。

保留期按文件创建时间计算；时间和总容量任一限制触发即删除最旧的自有日志文件。高流量时可能保留不足 7 天，文件粒度清理也可能提前删除文件中的较新记录。写入和启动时清理，空闲期间每小时检查一次。其他文件及符号链接不作为日志删除。

每条记录直接写文件，不跨调用缓冲；轮转和正常关闭时同步到磁盘。进程退出后通常可回溯已写出的记录；机器突然掉电可能丢失尾部。调用前已记录输入；正常完成或报错时记录完整或部分输出。强制杀进程时允许只有开始记录，不保存每个流式片段。

日志初始化会实际写入并同步，验证完成后移除探针内容；初始化失败会阻止服务启动。运行中写入失败不阻断业务，向 stderr 限频报告；后续写入恢复时记录丢失数量。数据库提交和日志写入不是一个事务，因此不能仅凭缺少日志断定操作没有发生。

查询会提示日志目录不可用、找不到关联历史、损坏尾行以及只有开始没有结束的调用。没有结束的调用可能仍在运行，也可能被中断。日志轮转可与查询并发；结果是当前数据库快照和尽力读取的历史证据，不是全局一致的审计账本。

## 隐私

默认保留完整聊天正文、上下文、回复、工具参数和返回内容。递归屏蔽 `Authorization`、`Cookie`、`Set-Cookie`、API key、token、password、secret 等明确字段，也处理工具参数中编码为 JSON 字符串的对象。配置中的模型 API key 和 Telegram token 在所有字符串中替换，序列化和脱敏不修改传给业务代码的数据。

普通正文里的未知凭证不做启发式识别。这些日志包含私人信息，不能直接当作公开附件；忘记一条记忆也不会清除此前聊天、数据库历史或尚未过期的日志。

## 分阶段交付与验证依据

| 阶段 | 交付 | 为什么需要这些测试 |
| --- | --- | --- |
| 日志基础 | JSONL、终端摘要、权限、轮转、保留、脱敏和配置 | 大上下文会超过 64 KiB；轮转可能误删文件；嵌套 JSON 与数字 ID 需要原样保留；创建文件成功但首写磁盘满或短写必须阻止启动；运行中写入失败仍继续业务 |
| 调用观测 | 模型/工具回调，主对话、格式整理、阅读与 review 接入 | 流式日志不能抢走业务响应，部分响应后报错须保留已有内容；并发调用不能串 ID；读取失败与缓存重读不能误报成功或增加请求；可用截断材料不能误报失败；未知用量不能显示为已报告 |
| 生命周期 | Telegram、Runtime 和 Store 语义日志 | 事务失败不能误报成功；过期回调不能误报回复已入队；远端发送成功而本地凭据失败必须可区分；普通聊天也必须关联到投递 |
| 事后查询 | 稳定数据库身份、只读 events/trace CLI | 查询不能恢复执行中的任务或创建数据库；换库后不能误关联旧日志；同一事件的兄弟任务不能混入目标任务；轮询和恢复证据不能漏掉，也不能掩盖历史缺失；容忍损坏尾行 |

验证使用临时数据库、受控模型/工具和本地 Telegram HTTP fixture，不消耗真实模型配额、不向真实 Telegram 发消息。全仓测试及 `go vet` 验证共用组件对 V1 的兼容性；相关包的 race 检查验证日志、流式回调和运行时的并发路径。
