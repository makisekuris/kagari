# condition trigger 设计讨论

状态：2026-11-13，W0 设计草案；W1 尚未开始。本文随时序修复实施推进，用于讨论代码执行层、业务目标和 W2 拆分。首个实际业务、条件输入、执行运行时和数值限制尚待确认。实施总顺序见 [路线图](V2-TEMPORAL-WATCH-ROADMAP.md)。

## 1. 业务完成条件

condition trigger 让一个尚未完成的 Task 等待必要条件，条件成立后继续原目标。成功不能只按“条件代码返回 true”或“发送唤醒消息”验收：必须沿用同一 Task，创建有来源的新 Run，保留已有成果和工作区，使用剩余预算，完成原任务并通过正常交付流程给出结果。

候选场景包括等待正式价格发布后补齐采购比较，或等待 CI/外部任务完成后读取结果并继续原任务。首例需要使用者确认实际来源、所需结果和访问范围；当前不把候选场景当成已确认需求。

需要由业务场景给出的事实：

| 问题 | 需要的答案 |
| --- | --- |
| 原目标是什么 | 原 Task 的交付要求和已有成果，等待结束后还需要完成的工作 |
| 等待对象是什么 | 明确的来源对象及身份，例如某个工作流执行、任务 ID 或厂商产品版本 |
| 怎样证明条件成立 | 来源字段、版本、采集时间和必要证据；只读成功不等于业务条件成立 |
| 什么情况下证据失效 | 例如目标分支 HEAD 改变、外部任务换代、价格适用区域变化 |
| 无法继续怎么办 | 到期、来源失败、预算不足或用户取消后的 Task 状态和用户反馈 |

## 2. 代码执行层的职责

建议允许主 Agent 为已授权目标登记条件代码，由宿主执行一次有界检查。循环的间隔、截止时间、重试、暂停和恢复由宿主持久调度；条件程序完成一次观察和判断后退出，不持有一个跨天存活的 sleep/while 工具调用。

| 组件 | 负责的内容 |
| --- | --- |
| 主 Agent | 根据原目标提出条件、登记等待、处理匹配证据并选择原目标内的下一步 |
| 条件代码 | 组合已授权的观察数据，返回未满足、证据不足或匹配及其证据引用 |
| 宿主能力接口 | 读取来源、记录来源身份和采集时间、保存证据；凭据留在现有来源拥有者处 |
| 调度与 Store | 检查尝试身份、时间及累计限制，原子保存匹配和固定接手身份，处理暂停与取消 |
| 现有事件与 Run 入口 | 校验授权和当前目标、排队接手、创建并开始原 Task 的下一 Run |
| 交付流程 | 结案保存交付意图、保序发送、保存回执并供 History 查询 |

这个分工允许代码表达业务条件，同时让程序不能自行选择另一个 Task、追加预算、发送结果或创建 Run。程序输出及来源文本都作为任务材料；授权来自登记时绑定的用户目标。

### 2.1 候选检查接口

接口尚未定稿。建议每次调用接收固定 Task/revision、触发定义版本、宿主时间和只读能力；程序通过能力读取来源，而不是自行填写可信来源身份。

```js
// 示例接口，尚未实现；外部任务场景也尚未选定。
function check(ctx) {
  const observation = ctx.read("external_task", { id: "authorized-job" });
  if (observation.status === "unknown") {
    return { outcome: "insufficient_evidence" };
  }
  if (observation.value.status !== "completed") {
    return { outcome: "not_matched" };
  }
  return {
    outcome: "matched",
    evidenceRefs: [observation.ref],
    resumeHint: "读取已完成任务的产物，继续完成原目标。"
  };
}
```

示例的 `resumeHint` 是原目标内的续跑建议。宿主必须检查返回的证据引用来自本次已授权读取，再保存匹配；不能把程序自己构造的 URL、时间或状态当作宿主已观察事实。读取故障和程序异常由宿主记为检查错误，不能统一转成 not_matched。

### 2.2 执行能力的选择

| 方案 | 适用范围与代价 | 当前判断 |
| --- | --- | --- |
| 成熟 JavaScript 解释器加宿主能力 | 条件可组合来源；依赖较集中，需要确定语言支持、打断机制和资源限制。嵌入解释器本身不等同于操作系统隔离 | 优先评估，待实际条件确认后选择现成库，不自写解释器 |
| 独立代码执行进程 | 可获得独立进程生命周期；增加运行时安装、进程回收、IPC 与平台支持工作，仍需明确文件、网络和凭据权限 | 若业务必须运行现有程序或需要进程资源隔离，再采用 |
| 固定条件枚举 | 少数确定来源容易实现，但每增加组合条件都需要扩展宿主代码 | 可作为对照，不以此预先排除用户提出的代码执行层 |

是否开放命令执行另作决定。执行一个已有只读状态查询程序与任意 shell 权限不同；条件检查可能因中断或重启重复执行，不能包含未经对账即可重放的写操作。若首个业务确实需要命令，必须确定命令身份、工作目录、环境、输出上限、进程结束和重复执行语义。

实现前需要确认单次检查时长、操作数、输出大小、并发度、累计用量及失败上限。具体默认值以首个来源和运行时能力为依据，本草案不套用其他项目的数值。

### 2.3 首轮选型建议

优先验证 Goja 加 Kagari 宿主能力。Goja 是纯 Go 的 JavaScript 引擎，可将 Go 函数提供给脚本；单个 Runtime 不能被多个 goroutine 同时使用，定时器及事件循环由宿主提供。建议一次检查使用一个独立 Runtime，只提供登记时允许的读取能力；下一次检查重新从持久记录启动。这与 Kagari 现有 Go 服务和持久任务入口衔接较直接，是当前的工程判断，尚未确定依赖版本。[Goja 项目说明](https://github.com/dop251/goja)

检查超时需要覆盖两层：JavaScript 执行可用 `Runtime.Interrupt` 打断；宿主读取函数必须另行遵守同一个检查 context。Goja 文档明确指出 Interrupt 不会中断正在执行的 Go 函数，因此不能只给 VM 设置一个计时器就宣称整个检查有界。语言调用栈上限也不等同于整个进程的内存上限；若首个业务要求独立资源隔离，需要评估进程方案。[Goja Interrupt](https://pkg.go.dev/github.com/dop251/goja#Runtime.Interrupt)

独立进程可对照评估 Deno：其文件、网络和环境访问需要显式权限，可减少脚本直接接触服务能力的范围；但允许启动子进程后，子进程不会继承 Deno 的权限限制。若采用它，Kagari 仍通过宿主接口提供带证据的读取，进程退出和结果协议由检查调度拥有；不能把开放 `--allow-run` 当作已解决命令权限。[Deno 权限说明](https://docs.deno.com/runtime/fundamentals/security/)

W1 获准后，运行时验证至少包含：真实业务条件可表达；条件代码无限循环能结束；宿主读取超时能结束；代码异常与 not_matched 分开；返回伪造证据引用被拒绝；匹配提交后重启不再求值；最终由原 Task 完成业务交付。当前仅记录方案，没有加入运行时依赖或开始 W1 编码。

## 3. 持久状态与交接

候选处理顺序：登记条件与外部等待状态同事务提交 → 来源事件完成 → 领取一次检查 → 事务外执行条件代码 → 原子保存匹配证据和固定接手身份 → 复核资格并入队条件触发事件 → 主 Agent 决策 → `ContinueTask` 创建原 Task 的下一 Run → 来源事件完成 → 执行前复核 → 正常执行及交付。

匹配后不重新执行已经成功提交的条件程序。资格复核检查当前目标、授权、预算、执行侧的暂停/取消状态和证据适用性；来源后来不再展示旧事件，不应使已经保存的历史事实消失。对依赖当前状态的证据，版本变化应阻塞或取代等待，不能偷偷把原匹配换成另一份证据。

固定接手身份需要贯穿事件和 Run。入队结果未知时先查询原身份；已有事件或 Run 时继续同一个对象，不能重新调用模型猜测先前是否已提交。`consumed` 只说明接手结果已记录；没有创建 Run 的接手也必须说明等待用户、阻塞或终止。

暂停、取消、到期和人工续跑需要按路线图的阶段表逐项确定，尤其是已经入队、已经创建 Run 但尚未实际执行这两个窗口。建议同 revision 的人工续跑取代旧触发记录，避免旧条件再次启动工作；该选择仍待讨论确认。

## 4. W2 拆分

所有子阶段依赖 W1 设计确认，用户可见行为依赖 F2–F4。共享类型与状态转换先由主 Agent 定稿，再按文件职责委派编码。

| 子阶段 | 实施范围 | 独立验收 |
| --- | --- | --- |
| W2.1 工具与查询 | 登记、查询、暂停、恢复、取消工具；只读诊断；上下文中的条件、证据和阻塞状态 | 授权来源正确；查询说明正在等什么及为何不能继续；不会将查询当成恢复授权 |
| W2.2 事件接手与幂等 | 条件触发事件身份、主 Agent 工具权限、固定续跑请求、Run 关联和来源事件完成 | 重复事件或中断恢复关联同一 Run；不扩大目标或增加预算；无 Run 时有明确接手结果 |
| W2.3 执行前校验与恢复 | ClaimRun、等待锁、实际开始的复核；预算记账；输入交接、成果和工作区继承；暂停取消 | 条件成立后取消仍能阻止未开始执行；恢复不复制 Run；预算不重置，后补材料不遗漏 |
| W2.4 业务完成与交付 | 首个真实场景全流程；通知抑制；附件与回执；Schedule occurrence 兼容 | 原 Task 达成业务交付，条件不重复触发，证据可追溯，投递失败可查询且不重复研究 |

W2.4 的成功标准是原业务目标完成。仅让解释器跑通、打印 matched、创建一个新 Task 或向主对话发送提示，都不足以关闭 W2。

条件匹配、Task 结案与交付完成分别验收。后续接入复用 `DeliveryProgress` 查询每段正文和附件的实际结果；渠道接受不表示用户已阅读。若已生成报告但附件失败，保留报告和匹配证据，通过原交付查询或用户授权的历史补发处理，不重新登记条件或重复执行业务研究。

各子阶段进一步按以下调用链落地；接口名和等待状态枚举由 W1 讨论决定，不能把这里的任务清单视为提前批准编码。

- W2.1 先定义来源身份与查询结果，再接工具权限和上下文卡片。登记同时写触发记录及 Task 等待状态；查询至少返回条件版本、锚点 Run、下一次检查、截止时间、已保存证据及当前阻塞。逐一检查 Task 查询、待处理材料、回复组关闭和等待提示的状态分支。验收使用同一来源重试、已结束/过期回调、其他 Task、用户查询后未授权恢复这四类调用。
- W2.2 先接固定来源事件，再接主 Agent 决策与 ContinueTask。分别测试匹配已保存但事件未入队、事件已入队未处理、Run 已创建而来源事件未完成三个中断位置。每次恢复都从保存的请求身份找到同一个接手结果；无 Run 的结果必须记录等待输入、阻塞或结束，不能只写 consumed。不得复用锚点 Run 的唯一事件槽，也不能伪装成直接用户消息。
- W2.3 先把执行前校验接到 Task 锁内的实际开始入口，再处理暂停/取消和预算记账。用阻塞点控制 ClaimRun、等待锁、拿锁后开始三个窗口；检查同一个 Run 的处理结果。之后覆盖后补材料的认领/释放、原工作区和成果继承、登记回调及接手决策的耗时、剩余预算不足与用户追加预算。暂停后的恢复是否复用已排队 Run，由 W1 的状态表确定。
- W2.4 把真实来源、条件代码、匹配证据、原 Task 续跑和结案连起来，再验证正常交付。结案使用已实现的 TaskSettlement/DeliveryIntent，通知保存用途和原 Task/revision/Run；不另建发送入口。验收同时断言业务结果、原 Task ID、唯一后继 Run、来源证据、选定附件和逐项渠道回执。若用户停止投递，业务计算仍按自身授权运行，结果保留且按交付规则抑制；恢复投递不会自动复活旧成果，需要显式补发。

每个子阶段的提交记录包含受影响调用入口、状态转换表、故障位置及实际测试结果。W2.4 还需覆盖 Schedule 产生的 Task：保留 occurrence 和冻结检查区间，外部新证据不能自动给旧区间增加覆盖进度。四个子阶段分别通过 review 后提交，不以一份大提交同时更换等待、授权、执行和交付语义。
